0. 问题

深交所的行情快照是 3 秒一个周期 推送的。交易所内部有多台前置机/编码机，
每台机器负责一批股票：同一台机器上的股票，快照会在同一个时间点被打包发出，
在同一条链路上到达我们的网卡。于是有一个可观测的现象：

同机器的股票，tick 到达时刻非常接近，而且是「一起抖」的——
机器忙一点，这一批股票全部晚到；机器闲一点，这一批全部早到。

反过来，只要能把这种「一起抖」量化出来，就能反推出交易所内部的机器分组。
这件事的实用价值在于：如果你只关心某几只票，知道它们在哪台机器上，就能知道
该订阅哪条组播流、该盯哪一段延迟；做行情延迟监控时也能按机器而不是按股票归因。

整体做两段：

  1. 第一段：读 tick 明细 → 提取每只股票的到达时间序列 → 两两相关系数 → 存 csv + 画到达时间图；
  2. 第二段：读相关系数 csv → 图论（全联通子图 / 团）聚类 → 画「3 秒折叠图」和「聚类图」。

1. 关键的建模选择：用交易所时间戳做批次键

落盘的 tick 里通常有两个时间，别搞混：

列 含义 例子
clock 本机收到这条快照的时刻，epoch 微秒 1548983031092679
time 交易所打的快照时刻，同一批发出的所有股票完全相同 08:34:27.000

一开始最容易想到的是「把两只股票的到达时间戳序列直接做相关」，但这没用——
时间戳单调递增，任意两只票的相关系数都接近 1，信息全在趋势里。

正确的量是两者之差，也就是这只股票这一批的链路延迟：

同一台前置机上的股票共享同一条发送链路：机器忙一点这一批全部晚到、闲一点全部早到，
所以它们的 latency 序列是”一起抖”的。两两做 Pearson 相关，同机器的票就会跳出来
（实测同机器 0.999，跨机器 0.03）。

time 同批完全相同这一点，还顺便给了我们一个天然的批次键。
早期版本没用它，而是把本机时间对 3s 取模、用 clock // 3s 当周期号，
对比下来批次键有三个好处：

  1. 不依赖「3 秒一个周期」这个假设。 盘前每分钟推一次快照时，取模口径会直接失效
    （见第 7 节模式 E），批次口径则完全不受影响——一批就是一批；
  2. 没有周期边界折返问题。 相位落在 0/3000ms 附近的机器，取模后会在 2999 和 1
    之间反复横跳，方差被放大到 ~1400ms，相关系数直接被打垮，得额外按圆周均值把它掰直；
  3. 不需要对齐 origin。 取模口径的周期号依赖一个人为选定的起点，批次键天然对齐。

所以现在的主路径是批次口径；只有当文件里没有交易所时间列时，才退回 3s 取模
（build_offset_matrix()，圆周均值那套补丁还留着）。

5. 调试过程中踩到的三个坑

这三个都是跑测试时真实撞上的，直接决定了脚本里几处看起来”多余”的代码：

  1. 周期边界折返。第一版测试里有一台机器怎么都聚不进去，查下来它的 offset 标准差
    是 1429ms（其他机器都是 ~20ms）——相位落在 0ms 附近，抖动一跨越边界就被取模翻到 2900+。
    加上 unwrap_cycle_boundary() 之后同机器相关系数从 0.79 回到 0.999。
    在折叠图里还能直接看到这台机器：它的色带同时出现在横轴的 0.0 和 3.0 两端。

  2. 样本量不够会产生虚假相关。机器抖动是自相关的 AR(1) 序列，两条独立的 AR(1)
    在只有 300 个周期时，虚假相关系数能冲到 0.5 以上。把周期数提到 1200（真实一天大约 4800 个周期）
    之后，跨机器相关系数的中位数掉到 0.014。结论：至少拿一小时的数据来跑，别拿几分钟的。

  3. 丢包必须成对剔除。用 DataFrame.corr(min_periods=...) 做成对剔除，
    而不是先 dropna() 再整体算——后者在几十只股票、各自随机丢包的情况下，
    会把大部分周期都丢光。

  4. to_numpy() 返回的是只读视图。unwrap_cycle_boundary() 里对 v[ok] 做原地赋值，
    在我本机（pandas 2.2.2，copy-on-write 默认关闭）跑得好好的，换一台开了 CoW 的机器就炸：

    Series.to_numpy() 默认尽量不拷贝，CoW 打开之后它直接把 writeable 标成 False
    来阻止你绕过 pandas 改底层数据；pandas 3.x 里 CoW 是默认行为，所以这个坑会越来越常见。
    解法是显式 to_numpy(dtype=float, copy=True)——凡是打算写的 numpy 数组，
    就不要指望 to_numpy() 给你一份可写的    。测试脚本开头也加上了
    pd.options.mode.copy_on_write = True，让这类问题在本机就能暴露，而不是等别人跑的时候才炸。

6. 拿到真实数据之后要注意的

6.1 时间戳单位：脚本自己数位数

单位这件事我来回踩了三次，最后的结论是不该让调用方去想它。
整数时间戳的位数已经唯一确定了单位：

位数 单位 例子
10 秒 s 1586478875
13 毫秒 ms 1586478875243
16 微秒 us 1586478875243015
19 纳秒 ns 1586478875243015000

所以 load_ticks() 默认 time_unit="auto"，取该列的中位数数位数自动判断
（用中位数而不是首行或极值，理由见第 7 节模式 D）。深交所落地的 tick 是 16 位微秒，
1548983031092679 对应 2019-02-01 09:03:51.092679（北京时间）。

两个相关的点：

  • 时区不影响相关系数。 pd.to_datetime(..., unit=...) 给的是 UTC naive 时间，
    比北京时间差 8 小时。算 latency 时要把它换算回北京时间才能和 time 列相减，
    所以有 --tz-offset（默认 8）；但相关系数只看相对抖动，时区偏移是个常数，加不加都一样。
  • 别让 pandas 自己推断时间戳列的 dtype。 float64 能精确表示的整数上限是
    2^53 = 9007199254740992（16 位），微秒时间戳刚好卡在安全线内侧，
    但纳秒时间戳会掉精度——实测 float(1586478875243015000) 回来会差 88ns。

6.2 其他

  • load_ticks() 里务必确认时间列是本机接收时间；如果抓包时间戳能用 PTP/硬件打点就更好，
    软件时间戳的抖动（几十 μs）对这里的 ms 级信号影响不大，但别用交易所时间戳。
  • 3s 周期只对快照行情成立；逐笔委托/逐笔成交是事件驱动的，
    这套方法不能直接套，需要换成「按固定时间窗计数再相关」的口径。
  • 开盘集合竞价、盘中临停、收盘阶段的推送节奏和连续竞价不一样，
    建议只取 09:30–11:30 / 13:00–14:57 的连续竞价段来算。
  • 交易所扩容或者主备切换之后分组会变，这个结果要定期重算，不能算一次用一年。
  • 如果发现某只股票同时和两个团都强相关，大概率是它被双发了（主备同时推），
    这种点在 clusters.csv 里会落到某一个团里，值得单独捞出来看一眼。

按经验，空白落在这三种模式里：

模式 A：offset 是常数（标准差为 0）

最常见的原因是时间列取错了：用了交易所打的 quote_time，它严格对齐 3s 边界，
取模之后每个周期都是同一个值——抖动信息已经被交易所抹平了。换成本机 recv_time 就有了。
这也是全文最关键的前提：没有本机接收时间戳，这套方法根本做不了。

模式 B：数据太短，min_periods 卡死

拿几分钟的数据试跑就会这样。前面第 5 节说过虚假相关要靠样本量压下去，
所以别靠调小 min_periods 来”解决”它，直接去取一小时以上的数据。

模式 D：个别脏行把整份文件带崩

上面那个自检的第一版是用 min() / max() 判断的，结果立刻被真实数据打脸：

56423 行里只有 2 行是脏的（一行 0、一行混进来的 10 位秒级值），
单位其实完全正确，却因为取了极值就把整份文件拒了；连报的位数都是错的，
因为 raw.iloc[0] 刚好取到那行 0。

真实的行情落盘文件里混几行 0、空值、或者单位不一致的记录太正常了，
所以判断单位必须用中位数这种抗异常值的统计量，而不是极值：

  • 中位数落在合理区间 → 单位是对的，个别坏行 [warn] 打印出来剔掉，继续跑；
  • 超过一半的行都不合理 → 那才是真的单位错了，抛异常并猜出正确单位。

教训是：校验逻辑本身也要对脏数据鲁棒。一个用极值做判断的”防御性检查”，
在真实数据面前比不检查还糟——它会把 99.996% 的好数据连坐掉，
而且给出一个指向错误方向的报错信息。

最后，[2] 那段的「两两共同非空周期数」值得单独看一眼：深交所对没有成交的冷门股
不一定每个周期都推快照，这些票覆盖率很低，和别人的共同周期数不够就整行 NaN。
这不是 bug，把它们单独挑出来或直接从矩阵里剔掉即可。

模式 E：盘前每分钟一次，把 3s 取模口径打穿

这个是真实数据里撞出来的，也是最终促使我换成批次口径的原因。

集合竞价之前，快照不是每 3 秒一次，而是每分钟把所有股票推一遍。
而 60 秒恰好是 3 秒的整数倍：

于是盘前所有 tick 都落在 3s 周期里的同一个相位上，clock % 3s 变成一个常数。
常数列的标准差是 0，Pearson 的分母就是 0——这正是模式 A 描述的那张全 NaN 的表，
只不过病因不是”时间列取错了”，而是”数据里混了另一种推送节奏”。

而批次口径根本不需要这一步：一批就是一批，每分钟一批和每 3 秒一批
在 latency = clock - time 面前没有任何区别。合成数据里我特意把两段节奏混在一起
（盘前 12 批 @60s + 盘中 1200 批 @3s）来固化这个行为：

1212 = 12 + 1200，两段都用上了，相关系数没有被盘前那段污染。

这件事的一般教训：当你的方法依赖某个周期假设时，先去确认这个周期在全时段都成立。
“盘中每 3 秒”是对的，但”全天每 3 秒”不是——而 60 是 3 的整数倍这个巧合，
让错误不表现为噪声，而表现为一个干干净净的常数列，看起来完全不像 bug。
数据里但凡有个现成的、语义明确的分组键（这里是交易所时间戳），
就优先用它，别自己从时间轴上硬切。

8. 快照不是每 3 秒都有：只在数据变化时才推

实际观察到的现象：同一只股票有时 3 秒更新一次，有时隔 6 秒、12 秒才更新一次。
合理的解释是交易所只在数据有变化时才推快照——没有成交、盘口没动的票就不推。
这条对算法有直接影响。

8.1 相关系数：只用两只票都有更新的批次

第一反应是对的：只有两只票都出现的批次才是有效样本，其余必须忽略。
这一步其实已经在做了——DataFrame.corr(min_periods=...) 用的就是成对剔除
（pairwise deletion），而不是先 dropna() 再整体算。所以口径本身不用改。

但光有这一步不够，因为能配对的点本身会不够。拿”按活跃度随机跳过批次”的
合成数据扫一遍（1200 个批次，更新率各不相同）：

更新率 两两共同批次(中位) NaN 对数 ARI
0.95 / 0.5 / 0.25 286 0 / 276 1.000
0.2 / 0.1 / 0.05 11 251 / 276 0.062
0.1 / 0.05 / 0.03 3 276 / 276 0.000

更新率 0.1 的两只票，1200 批里只共同出现约 12 次，连 min_periods=30 都够不着，
于是整张表 NaN，聚类直接崩。

8.2 两条走不通的路

**调小 min_periods**：重叠只有 5 个点时，跨机器相关系数能虚高到 0.98
（本来只有 0.3），阈值再怎么调都分不开。样本量不是可以牺牲的东西。

插值补齐再算相关：把每只票的延迟路径插到完整批次网格上，看似解决了 NaN，
实测是把信号插没了——

方法 同机器最小 跨机器最大
原样 Pearson 0.9994 0.738
插值后 Pearson 0.678 0.765

两类分布直接重叠，比不做还糟。插值凭空造出来的平滑，对同机器和跨机器是一视同仁的。

8.3 走得通的路：改用需要更少样本的估计量

Pearson 之所以要 30 个点，是因为它估的是相关性——一个噪声量。
但同一批发出的股票，它们的延迟水平本来就几乎相同，这是近乎确定性的关系，
共同出现几次就能判：

方法 同机器 跨机器 可用对数
Pearson(min_periods=30) 最小 0.9994 最大 0.738 25 / 276
延迟水平距离 median|Δlat| 最大 79us 最小 383us 211 / 276

5 倍的间隔，而且只要求共同出现 5 次。所以正确的做法是两个证据互补：
重叠够就用相关系数（对基准延迟接近的机器也有分辨力），重叠不够就退到水平距离，
阈值用那些”重叠够、已经判定同机器”的对来自标定，而不是硬编码一个 us 数。

还有一点要注意：**”重叠不够所以不知道” 和 “确定不是同一台机器” 是两回事。**
现在的严格团聚类把 NaN 当成”没有边”，一个 NaN 就能把一个真实的团拆散，
这也是上面 ARI 掉到 0.062 的原因之一。

8.4 画图：--only-common-batches

同样的问题也出现在到达时间图上。各股票更新批次不一致时，直接画出来每行疏密不同，
纵向根本没法对比——你分不清”这只票这一批晚到了”和”这只票这一批压根没更新”。

只保留所有入选股票都有更新的批次，这样图上每一条竖线都是一次真正的”同批”，
纵向对齐才有意义。不加这个参数就是全画（默认），两种视图各有用处：
全画能看出各股票的活跃度差异，只画共同批次才能看清同批内部的先后次序。

入选的票里只要有一只特别不活跃，共同批次就会所剩无几，所以这个参数配合
--symbols-file 用最合适。真的一个共同批次都没有时会直接报错，
并把更新最少的那几只列出来，而不是画一张空图。

8.5 看批内结构：--n-batches

横轴按批次数自动拉长解决的是”全天节奏”，但想看一批内部各股票的先后次序，
再长的图也没用：单批只有几毫秒，全天 4800 批铺开时它连一个像素都占不满。

这时候图才有意思——8 毫秒的窗口里能直接看到机器的阶梯结构：
每台机器的股票是串行发出的，在图上是一条斜线；机器与机器之间有明显的跳变。
换句话说，聚类算法要靠 1200 个批次的相关系数才能推出来的分组，
在这张图上肉眼就能看个大概。

几点用法上的注意：

  • --n-batches 2 会把两个相隔 3 秒的批次画在一起，中间全是空白，
    批内结构反而看不见了。要看批内就用 1，要看节奏就别限制批次数。
  • 配合 --from-time 可以定位到具体某一批，比如
    --from-time 09:35:00 --n-batches 1；
  • 盘前那段是每分钟一批，所以”相邻两批”在盘前是 60 秒、盘中才是 3 秒——
    写测试时我就在这里断言错了一次（拿前两批去量，量到 60s）。

8.6 单批次时按到达先后排纵轴

--n-batches 1 画出来的图还有一个问题：纵轴默认按股票代码排。
而真实市场里机器和代码段是交错的——不是 000001–000100 一台机器这么整齐，
所以按代码排会把机器结构彻底打散。

改成：只画一个批次时，纵轴自动按这一批的到达先后排序。
机器是串行发包的，排完之后同机器的票天然相邻。

拿”40 只票随机分给 4 台机器、代码完全交错”的数据量一下，
指标用「机器标签的连续块数」，理想值就是机器数 4：

纵轴排序 连续块数
按到达先后 4（每台机器正好一块）
按股票代码 30（被打散）

也就是说，聚类算法要算 1200 个批次的相关系数才能推出来的分组，
在这张排好序的单批图上肉眼直接可读。这张图现在成了聚类结果的独立验证：
两边对不上，说明其中一边有问题。

排序策略由 --sort 控制，默认 auto：

  • auto：单批次时按到达先后，否则按代码/清单顺序（默认）；
  • arrival：一律按到达先后；
  • symbol：一律按代码或 --symbols-file 里的顺序。

多批次时默认不按到达排，是因为那时”到达先后”取的是第一批的次序，
对其余批次未必成立，排出来容易让人误以为这个次序是稳定的。
真要看稳定性，就固定 --sort arrival 翻几个不同的批次对比。

9. 单批次的整齐，能代表真实机器分组吗

把一个批次按到达时间排好序之后，同组的票挨得非常近、组之间有明显空档，
看起来很有说服力。但这里有个必须自己先问一遍的问题：

这是真实的机器分组，还是只是这一批的偶然次序？

交易所完全可能每批换一个发送顺序。那样的话每一批都会”看起来很整齐”，
但组的构成每批都不一样，单批次的图就什么也证明不了。
区分二者只有一个办法：看跨批次稳不稳定。

9.1 逐批分组表

新写了个 batch_groups.py：对每个批次独立按到达间隔切一次组，
再把结果拉成一张 股票 × 批次 的表。

横着扫一行，就知道这只票的归属跨批次稳不稳定。切组阈值不硬编码微秒数，
而是取「本批相邻间隔中位数的 --gap-k 倍」——机内串行发包相差几十微秒，
换机器是几百微秒的跳变，但具体数值随市场和时段变，不该写死。

9.2 共识分组才是结论

单批次的分组只是一次观测，可以拿去用的是共识分组：
统计每两只票「在都出现的那些批次里被分到同一组」的比例，
比例够高才连边，再取连通分量。

产出三个文件：逐批分组表 batch_groups.csv、两两同组比例 batch_group_share.csv、
每只票的稳定性汇总 batch_group_summary.csv（含共识组号、同组率、出现批次数）。
同组率明显偏低的票值得单独看——它可能被双发，也可能刚好在两台机器的边界上。

9.3 关键是这个检验得有鉴别力

一个永远回答”稳定”的检验没有任何价值。所以测试里必须同时喂一份
没有稳定分组的数据：把每个批次的延迟随机重排（延迟的分布完全不变，
只打乱谁是谁），看它会不会否定。

数据 共识组数 同组率中位数
真实机器分组 4（与真值 ARI = 1.00） 1.000
每批随机重排 20（每只票自成一组） 无同组成员

重排数据下每只票都被判成孤立点，正是我们想要的否定。
这条测试比那些”跑通了”的测试重要得多——它验证的是结论的可证伪性。

顺带一提，写这段验证脚本时我又踩了一次 to_numpy() 的只读视图
（就是「模式 F」那个坑），v = mat.to_numpy(copy=True) 才能原地重排。
自己写过的坑，换个场景照样会踩。

9.4 用聚类结果给到达图排序：--clusters-file

第二段脚本产出的 clusters.csv 可以直接喂回第一段，用来给到达时间图排序上色：

纵轴变成「先按簇、簇内按到达先后」，每簇一种颜色，簇边界画一条横线。
这样这张图就成了聚类结果的独立检验：

  • 同簇的票应该连成一条不间断的斜线——因为机器是串行发包的；
  • 某只票的点明显偏离自己那一簇，就是它被分错了，或者它被双发（主备同时推）；
  • 簇与簇之间应该有肉眼可见的空档，空档消失说明两台机器的基准延迟太接近，
    这时相关系数还能分开，但单批次的间隔法（第 9.1 节）就不可靠了。

注意两件事。一是得跑两遍第一段——聚类结果是第二段才产出的，
所以工作流是”先算相关系数、再聚类、再回头画图”。
二是 read_cluster_file() 和 load_corr() 一样，第一列必须按字符串读，
否则 000002 又会变成整数 2，跟 tick 里的代码对不上（见「模式 G」）。
同一个坑在这个项目里已经出现三次了，凡是从 csv 读股票代码的地方都要留神。

10. 增量聚类：开盘第一批播种，之后就近归组

相关系数法有个硬性前提：两只票要有足够多的共同批次。
但深交所只在数据变化时才推快照，冷门票的共同批次可能只有个位数（第 8 节），
这条路就走不通了。

换个思路——不要求两只票同时出现，只要求新票出现时已分组的票也在场：

  1. 取开盘后第一个批次，按到达间隔切组作为种子；
  2. 按时间顺序往后遍历，用这一批里已分组股票算出各组延迟中位数；
  3. 这一批里新出现的未分组股票，归到中位数最近的那个组；
  4. 直到所有股票都有归属。

这个条件比”两两共同出现 30 次”宽松得多，所以在稀疏数据上反而更稳。

产出里除了组号，还有 assigned_at（这只票是在哪一批被归类的）和
dist_us（归类时离组中位数多远）。dist_us 明显偏大的票要单独看一眼。

10.1 什么时候它比相关系数法强

用”一半股票很晚才首次出现 + 更新稀疏”的合成数据（正是它要解决的场景）：

方法 ARI
增量聚类 1.0000
相关系数 + 团聚类 0.5598

差距全在那些晚出现、更新少的票上——它们和别人的共同批次不够，
相关系数根本算不出来，而增量法只需要它出现的那几批里有已分组的票在场。

10.2 组数固定为第一批切出来的组数

默认不新建组：组数就是种子批次切出来的组数，之后出现的票一律就近归入。
这是有意的取舍——组数可控、结果好解释，代价见下。

“组数太多”最常见的原因不是新建组，而是种子批次被切碎了：
自动阈值（组内间隔中位数的 --gap-k 倍）在真实数据上很脆弱，
机内偶尔有个大一点的空档就被当成机器边界。所以脚本会先把最大的那些空档打出来：

667 639 602 之后陡降到 42——三个大空档、四个组，一目了然。
看到这个就可以直接定组数，不用去调阈值：

--n-groups N 就在最大的 N-1 个空档处切，组数由你定。

归组距离上限仍然有用，但不再用来新建组，而是用来报警。
阈值用种子批次里组内相邻间隔的中位数自标定（默认 20 倍）——
机内串行发包的间隔本身就是这台机器的”尺子”：

这条警告正是上面那个取舍的代价浮出水面的地方。构造”第 4 台机器整体缺席
种子批次”的数据：

设置 组数 ARI
默认（不新建组） 3 0.6931
--allow-new-groups 4 1.0000

10.3 一个踩到的坑：别在首次出现时就下结论

安全阀第一版是”首次出现就判，判不进就记一次待定”，结果上面那个缺席场景
只拿到 ARI 0.69，而且新组一个都没建。

原因是机器抖动有几百微秒，量级和机器之间的基准延迟差（700us）相当。
新票首次出现的那一批，抖动完全可能让它离错误的组更近，于是被当场归错，
再也没有翻案机会。

改成攒够 5 次观测、取距离中位数再判，抖动被平掉，ARI 回到 1.0，
新组也正确建了出来。教训是：在线算法里”第一次看到就决定”是最脆弱的环节，
只要观测本身带噪声，就得让它攒够证据再落子。

11. 上真实规模：两处会卡死的地方

前面所有验证都是几十只票的合成数据。真实的深市有几千只票、全天几千个批次，

11.1 O(N²) 的 Python 双重循环

batch_groups.py 里算两两同组比例的那段，写的是最直白的双重循环：

2000 只票 × 200 批就要 31 秒，而真实规模还要再大一个量级——
卡在 [stability] 那一行不动，而且因为没有任何进度输出，看上去像是死循环。

改成稀疏矩阵乘法。关键是把”同组”表示成指示矩阵：

  • P[股票, 批次] = 该股票在该批次出现过 → P @ P.T 就是两两共同出现的批次数；
  • X[股票, (批次,组号)] = 该股票在该批次属于哪个组 → X @ X.T 就是两两同组的批次数；
  • 两者相除就是同组比例。

连通分量也从 networkx 换成 scipy.sparse.csgraph.connected_components。

规模 改之前 改之后
2000 只 × 200 批 31.4s 0.38s
5000 只 × 300 批 （没跑完） 3.0s

ARI 仍然是 1.000——只是换了算法，没换口径。

另外加了 --sample-batches（默认 300）：稳定性统计量不需要全量批次，
全天 4800 批和随机抽的 300 批给出的结论没有区别。
还有 --max-share-csv：N×N 的同组比例矩阵在几千只票时是几十 MB 的 csv，

12. 单批切出的组比机器多：合并与漂移

实盘上撞到的现象：单个 3s 批次里结构非常规整，能切出 57 个组，
但把第一批的结果套到全天就对不上了。真实机器数应该远少于 57。

两个原因叠在一起：

  1. 一台机器在一批里不是连成一片。 机内多队列/多线程发包，
    会分成若干子块，子块之间也有空档，于是按间隔切就切多了；
  2. 后面在漂移。 各机器的基准延迟随负载缓慢变化，组间空档忽宽忽窄，
    子块之间的相对位置甚至会换序——所以第一批的切法套不到后面。

12.1 合并的依据：不看间隔，看同步性

合并不能再靠”间隔够近”——漂移之后间隔本来就不可靠。要看的是时间上的同步性：

把每个种子组在各批次的延迟中位数拉成一条时间序列，
同一台机器的子组，这些序列会一起抖。两两算相关系数，高的并成一台机器。

关键在于用组中位数而不是单只股票：组里有几只到几十只票，
中位数每个批次都算得出来，对稀疏更新免疫——这正是第 8 节那个”共同批次不够”
的问题在这里不复存在的原因。

用”12 台机器 × 每台 5 个子块 + 基准漂移”的合成数据验证：

组数 与真实机器的 ARI
单批间隔切（种子） 21 0.7748
合并后 12 0.9761

同机器的组对相关系数 0.85–0.99，跨机器最大 0.62，中间有很宽的间隔。

12.2 阈值要在上半区找

自动阈值这里踩了个坑。同一台机器的子组共享机器抖动，相关系数必然很高，
所以判别边界一定在上半区；而跨机器的对大量堆在 0 附近，
在全域找最大间隔（或者用 Otsu）都会被它们拽下来：

取阈值的方法 阈值 结果
全域最大间隔 0.458 10 台（并错了），ARI 0.824
Otsu 0.324 10 台，ARI 0.824
只在 [0.5, 0.98] 里找断崖 0.736 12 台，ARI 0.976

教训是：自动阈值不能脱离物理含义去套通用算法。 Otsu 是个好方法，
但它假设两类的规模可比；这里跨机器对的数量是同机器对的几十倍，
先验就不对称，直接用就会偏。

13.1 总览：这一刀切得对不对

13.4 一个我判断错了的地方：去共同因子

交换机/上游拥塞会让所有机器一起抖，把跨机器相关系数整体抬高。
我一开始想当然地建议”按批次减去股票横截面中位数”——实测是三种方案里最差的。

原因：横截面中位数本身就是中间那台机器的延迟水平。减掉它，
等于把那台机器的抖动取负号注入到所有股票里，凭空制造出共同成分。

用”同机器最小相关 − 跨机器最大相关”这个可分性间隔来衡量（越大越好）：

方案 无共同因子 有共同因子
不去均值 0.343 0.162
减股票横截面中位数 0.134 0.133
减各组中位数的等权平均 0.311 0.431

正确做法是按组等权平均：它是对多台机器取平均，单台的抖动被 1/√G 压下去，
所以既不注入噪声，又能在真有共同因子时把它扣掉。改成默认方案之后，
组 0 的非成员相关中位数从 +0.638 降到 −0.097，
后续的全局重归属需要纠正的票也从 25 只降到 4 只。

教训：**”去掉共同成分”这类操作不是免费的**，估计量选错会把信号一起抹掉、
甚至注入新的伪相关。凡是这种预处理，都要有一个”可分性”指标来验证它到底帮了还是害了，
不能凭直觉。

14. 子组每批都在变：线程划分是动态的

前面 §12 的假设是”子块是稳定的”——一台机器固定分成几个子块。
但更贴近实际的模型是：机器每个批次把「这批要更新的」股票分给若干个线程，
线程数还会变。于是子组的构成每批都不一样，稳定子块根本不存在。

这个假设对前面的方法是毁灭性的。按这个模型造数据（10 台机器 × 40 只票，
每批随机切成 1–6 个线程）实测：

逐批共识 min_share=0.5 201 0.3924

14.1 换一条更弱但更可靠的性质

稳定子组没有了，但这条仍然成立：

不同批次的线程划分不同，正好让同机器的股票通过不同的”中间人”串起来。

15. 并查集聚类：任意批次同子组即同机器

§14 的 thread_union.py 是先算两两同组比例、再按阈值连边。
但既然规律本身是”只要在任意一个批次里同属一个子组，就是同一台机器“，
那就没必要绕比例这一步——直接把”同子组”当作等价关系的生成边，用并查集求闭包。

15.1 只连相邻对

子组内只连相邻的两只（按延迟排序后），不是两两全连。
一个大小为 k 的子组，两两全连是 k(k-1)/2 条边，只连相邻是 k-1 条——
连通分量完全一样（一条链已经把它们连通了），但几千只票 × 几千批次时，
前者会直接把内存吃光。

这也是它比 §14 那套快得多的原因：thread_union.py 要算 N×N 的同组比例矩阵，
这里只需要一个边计数器，边数正比于”票数 × 批次数”而不是”票数²”。

15.2 “任意批次”这个口径的代价

并查集是不可逆的：一条误连就永久把两台机器焊死。
两台机器的延迟范围一旦有重叠，就会偶发地把对方的票切进同一个子组。

所以脚本同时统计每条边被多少个批次支持，并扫 min_count。
这两个数字的对比非常说明问题：

数据 只被 1 批支持的边 min_count=1 的结果
不重叠 0.0% 10 组 ✓
轻微重叠 24.6% 1 组（全崩）
严重重叠 26.8% 1 组

“只被 1 批支持的边占比”是个很好的早期预警：干净数据里它接近 0，
因为真实的同机器边有成百上千个批次支持；这个比例一高，就说明存在大量偶发误连。

15.3 自动选 min_count

既然 min_count=1 会塌，就扫一遍取组数最稳定的平台
（按 min_count 的对数跨度算宽度，因为支持数是指数分布的）：

数据 自动 min_count 组数 ARI
不重叠 5（平台宽 2.48 量级） 10 1.0000
轻微重叠 18（平台宽 0.32，会报警） 10 1.0000
严重重叠 找不到平台 拒绝输出 —

轻微重叠那档很有意思：严格按”任意批次”（min_count=1）会全崩，
但把门槛提到 18 个批次之后，完全还原了 10 台机器。
所以规律本身是对的，只是”任意”这个词在有噪声的真实数据里要读作”足够多次”。

严重重叠时脚本直接 SystemExit 并说明改用 merge_drift.py，不写任何结果文件。
这是有意的——留下一个看起来正常的 csv，比什么都不留危险得多。

15.4 把所有边导出来：edges.csv

union_cluster.py 会把每一条边写进 edges.csv：

列 含义
a / b 两只股票
n_batches 这条边被多少个批次支持
first_batch / first_time 第一次出现在哪个批次、几点
last_batch / last_time 最后一次
first_gap_us 第一次同子组时，两只票的到达间隔
min_gap_us 历次同子组里最小的间隔
cluster_a / cluster_b / cross_cluster 最终分组，以及这条边是否跨组

跨组的那些边就是被 min_count 挡掉的——排序看一眼，能确认挡掉的确实都是偶发的。

15.5 为什么”任意批次”必然失败

有了这张表就能回答一个关键问题：能不能只看单个批次，判断一条边是真是假？
拿有 ground truth 的数据对照（机器间距 900us，轻微重叠）：

判据 真边 误连边
间隔 ≤ 5us 6953 6827
间隔 ≤ 10us 7753 9076
支持 ≥ 5 批 7672 968
支持 ≥ 18 批 4866 0

单批的间隔完全没有区分力——5 微秒以内的边，真假各占一半。
误连边的最小间隔中位数是 4us，比真边的 2us 还大不了多少：
两台机器的延迟范围一旦在某一瞬间交错，它们的票就是真的挨在一起，
不存在”看起来勉强”这回事。

只有重复出现能分开：支持 18 个批次以上的边里，误连是 0 条。

所以规律该这样表述：不是”在任意一个批次里同子组”，而是
“在足够多的批次里反复同子组“。前者在有重叠时必然把所有机器焊成一片，
后者才是可用的判据。脚本里那张支持数直方图就是用来看这件事的：

干净的数据（机器延迟范围互不重叠）是单峰的，”1” 那一档几乎是空的；
一旦看到 “1” 处有个大尖峰，就说明存在大量偶发误连，必须提高 min_count。

16. 只看交易时段：--session

前面几节反复撞到同一件事：盘前的数据和盘中不是一回事。

  • 盘前是每分钟推一次，不是 3 秒（§8 模式 E），3s 周期假设直接失效；
  • 盘前一次推全市场，各机器的负载、排队深度和盘中完全不同，
    延迟的绝对水平没有可比性；
  • 集合竞价期间的推送节奏又是另一套。

这些数据混进来，相关系数、子组切分、同组比例全都会被污染。
所以所有脚本统一加了 --session，默认只保留连续竞价：

取值 时段（北京时间）
continuous（默认） 09:30–11:30，13:00–14:57
full 09:15–11:30，13:00–15:00（含集合竞价与收盘竞价）
am / pm 只要上午 / 只要下午
all 不过滤

时段内没有数据时会直接报错，并把数据实际覆盖的时间范围打出来——
这比返回一张空表有用得多：

分时段跑还有个额外用处：上午和下午各跑一遍，看分组是否一致。
机器分配在盘中通常不变，所以 --session am 和 --session pm 的结果应该高度一致；
不一致就说明中午发生了切换，或者你的方法在这份数据上不稳。
这是不需要 ground truth 就能做的交叉验证。

16.1 顺带修好的 diagnose.py

加 --session 时发现 diagnose.py 从 §12 换批次口径那次起就坏了：
load_ticks() 的签名从 (csv, symbol_col, time_col, time_unit, date)
变成了 (csv, symbol_col, clock_col, exch_time_col, time_unit, ...)，
而 diagnose.py 还在按老位置传参——time_unit 被当成了 exch_time_col。

它不报错，只是安静地跑出莫名其妙的结果。位置参数在重构中最容易出这种事：
类型对得上、参数个数也对得上，于是没有任何一层会拦住它。
教训是改函数签名时要把所有调用方都跟一遍，而不是只跟”主流程”用到的那几个。

16.3 一个没走下去的思路：用绝对间隔切机器

中途观察到子组之间的间隔是双峰的——有些差 0.01s，有些差 0.3s，
直觉上”0.3s 是机器边界、0.01s 是机器内部的线程边界”，
那就可以用一个绝对阈值直接把机器切出来，比相对规则（中位数 × k）稳。

但这个思路站不住：0.3s 的空档也可能只是那段时间没票要发。
快照只在数据有变化时才推（§8），冷门时段一台机器可能整整几百毫秒没有任何输出。
拿间隔当机器边界，就会把”正好安静了一会儿”误判成”换了台机器”，
而且这种误判在成交清淡的时段会系统性地增多。

间隔只能说明”这两只票之间有个空档”，不能区分空档的成因是
“换机器了”还是”没数据”。要区分这两者，还是得回到时间维度上的重复性：
同一台机器的票会反复紧邻出现，而空档的位置每批都在变。
