目录形态、多段文件、store 级独占单写者、按记录大小分流、元数据与数据分离。
崩溃可恢复，支持保留与回收，全局总序成立。

  • 并发模型：单进程 · 多线程；独占粒度 = 整个 store
  • 记录长度：几 B ~ 1 MB（重尾）
  • 持久化：O_DIRECT + FUA + 前缀顺序 ack（不使用 fsync 作为提交屏障）

这个方案的出发点是一句观察：shard 的存在理由是「多个独立的锁域」，而单写者只有一个锁域。
于是 shard 整体删除，它带走的最大语义损失（跨 shard 无序）一并消失；
segment 留下来，分片多段方案的全部可运维性保留。
在此之上加一件单写者独有的事：按记录大小分流，消除重尾分布下的队头阻塞。

1. API 语义与文件格式

API 契约

append 的返回即代表已持久化。 没有单独的 sync() / flush() —— 返回本身就是持久点。
数据未落盘之前该调用必须阻塞。

不变式
A0 整个 store 同一时刻至多一个 writer 进程。raf_open 拿不到独占锁即失败，不阻塞、不排队
A1 append 返回 ⟹ 该记录已持久；崩溃重启后必定能通过返回的 Index 点读到
A2 append 未返回（阻塞中崩溃）⟹ 无任何承诺，该记录通常丢失
A3 append 返回 IO 类错误 ⟹ 该记录是否可见未定义；重试需自带幂等键
A3’ append 返回 EAGAIN（有界队列已满）⟹ 确定性地未写入，可安全原样重试。与 A3 必须是两个错误码
A4 调用期间 buf 必须保持有效且不被修改 —— 实现为零拷贝，IO 直接引用调用方内存
A5 调用不可取消、不可超时返回；一旦进入队列就必须等到终局
A6 顺序：所有记录有唯一的全局顺序（入队时由单一计数器分配 record_id），迭代严格按该顺序返回。分流不破坏它 —— 见下面的「分流为什么不丢顺序」
A8 ack 是按记录的，可见性是按前缀的。 append 返回只要求该记录自身持久（点读立即可用）；迭代只到 visible_id = 最大的 i 使得 0..i 全部持久。两者可以短暂不一致
A7 迭代是 at-least-once：batch 完整落盘但 visible_id 未及发布时崩溃，恢复后该批变为可见，而 append 从未返回。上层需自带幂等键去重

吞吐的直接后果： 因为 append 阻塞，单个调用线程的吞吐上限 = 1 / 端到端延迟。
要打满设备必须有足够多的并发调用线程，由各流的 I/O owner 攒批摊销。

A8 是本方案新增的一条，值得单独读。 前面几个方案把「已持久」和「可迭代」绑成了一件事，
代价是一条记录的 ack 要等整条前缀。这里拆开之后，一条 3 字节记录的 ack 只等它自己那批，
而迭代的线性语义由 visible_id 独立维护 —— 这正是分流能成立的前提。

目录布局

结构

三条格式取向

  • F1 数据文件零元数据。 长度在 .idx 里，校验在 batch 级或（大记录）每记录一个 crc。
    数据区永远不被扫描，空洞是纯空间泄漏，不影响正确性。
  • F2 恢复只读 .idx。 .idx 对小记录约 1-2 B/条、对大记录约 6 B/条，
    恢复成本与数据量无关。对比：分片多段方案必须读完整批 payload 才能验 batch_digest。
  • F3 只有一处原地重写：IdxHeader。 双缓冲 + crc，任一份撕裂都不影响另一份。

校验分两档（承接分片方案的改动 ④）

档位 数据文件里 .idx 里 点读怎么验
小记录（< 阈值） 纯 payload varint len 读整个 batch 的 data 区间（有界，≤ 批大小）验 data_crc，顺带返回目标记录。仍是 1 次 IO
大记录（≥ 阈值） 纯 payload varint len + crc32c 读该记录自身，验自己的 crc。不必为一条 1 MB 记录重算整批 digest

小记录不付 per-record crc 的 4 字节 —— 几字节的记录付不起。它的完整性由所在 batch 的 data_crc 覆盖：batch 不完整则整批不可见，per-record crc 是重复投保。

分流为什么不丢顺序

这一步只有单写者做得到。 分片多段方案里 shard 分属不同进程，没有共同的计数器，
所以它的分片是真的把全局序永久排除了；这里的分流只是把一条有序序列拆成两条有序子序列，归并即可还原。

2. 写入与读取流程

写入

为什么不用 fsync： 它是屏障，拿不到两个同时在飞的持久点，单流提交速率被钉死在 1 / fsync延迟。
换成 FUA 后，持久化语义随每个写命令走，batch k 和 k+1 可以同时在飞。乱序落盘由第 5 步兜住：
batch 链的前缀持久性由 ack 规则保证，而不是由提交顺序保证。 孤儿 batch 不可能出现（batch_seq 不连续即判为链终点），但设备队列被填满了。

为什么要分流（本方案的主要新增）： 重尾分布下，一条 1 MB 的记录混进小记录的批里，
会让同批所有几字节的记录一起等那 1 MB 落盘 —— 队头阻塞，延迟被最大的那条记录支配。
分流之后：

混在一条流 分流
3 B 记录的 ack 延迟 等本批最大记录的 IO 只等小批自己的 IO
小批的典型大小 被大记录撑大，忽大忽小 稳定，可按延迟目标调
大记录 被小记录的攒批窗口拖延 单独成批，立即提交

代价是多一条流的零件，以及 A8 那个「ack 按记录、可见性按前缀」的概念拆分。

读取
点读 验 index_checksum → 验 store_uuid → 定位 stream/segment → 与 visible_id / 已提交边界比对 → 1 次 pread → 小记录验所在 batch 的 data_crc，大记录验自身 crc → 返回。数据文件无任何 framing 需要解析
迭代 Snapshot = 一个 u64 visible_id → 两条流各自顺序解析 BatchMeta → 按 record_id 二路归并 → 产出 (Index, payload)，严格全局序
顺序 严格全局写入序（A6）

Snapshot 从分片方案的「每 shard 的 segment 列表 + 各自 committed_end」降成一个整数。
这是删掉 shard 最直接的收益之一。

visible_id 的发布

shm 不存在或已失效（写进程不在）时，reader 退化为自行读两条流的 IdxHeader 并走尾部验证
—— 滞后一个 IdxHeader 周期，但永不给出不安全的边界。shm 只是加速，正确性不依赖它。

恢复

第 4 步是必须的，且它的开销是有界的。 一个 batch 的 .idx 已持久但 .dat 没持久时，
该批从未被 ack，但 BatchMeta 看起来完全合法。若不验数据，这些记录会变成可见但读不出来
（点读时 crc 失败）—— 比 at-least-once 更糟。验证范围只需覆盖崩溃瞬间的在飞窗口，
64 MB 在 2 GB/s 下约 32 ms。

第 5、6 步合起来是从分片多段方案继承的最漂亮的一点： 撕裂的尾巴原地冻结、永不追加，
于是既不需要 truncate，也不存在「新写入落到旧 in-flight IO 落点上」的竞态 ——
那块空间再也没有人会写。前几个方案里的 GAP_BOUND / MAX_INFLIGHT / 宽限期在这里整类消失。

原子性

操作 必须的序列
新建 segment create + 写 IdxHeader[0] → fsync 文件 → fsync small/ 或 large/ 目录
轮换 IdxHeader 写另一份 → FUA。无需 rename、无需目录 fsync（定位置覆写，双缓冲兜底）
segment 回收 先更新前继段的 predecessor_seq 链 → fsync → 再 unlink → fsync 目录

漏掉建段时的目录 fsync，后果是崩溃后 IdxHeader 引用了一个并不存在的 .dat 文件。

3. 好处与坏处

好处

  • 删掉 shard，换回全局总序。 shard 的存在理由是多个独立锁域，单写者只有一个锁域。
    分片方案永久失去的 A6 强语义在这里回来了，而且没付任何锁的代价。
  • 数据文件零 framing。 4096 字节的 payload 正好占一个扇区；1 MB 记录连续存放、点读无需解析。
    几字节的小记录在 .dat 里就只占几字节。
  • 恢复成本与数据量无关。 只读 .idx（1-6 B/条）+ 在飞窗口的数据校验。
    分片方案必须读完整批 payload 才能验 batch_digest。
  • 按大小分流消除队头阻塞。 3 字节的 append 不再等 1 MB 的 IO。这是重尾分布下最直接的延迟收益，
    而且只有单写者做得到（需要一个全局 id 计数器来保证归并后仍是全局序）。
  • Snapshot 降为一个 u64。 不再是「每 shard 的 segment 列表 + 各自边界」。
  • 取消 checkpoints/ 目录。 IdxHeader 双缓冲就是 checkpoint，少一种状态、少一套原子性要求。
  • 单流也能 QD > 1（FUA + 前缀顺序 ack），不必靠加分片换吞吐。
  • 撕裂尾部冻结 + 新建段 ⟹ 不需要 truncate，不需要任何宽限期或在飞 IO 落点推算。
  • 保留策略与空间回收齐备（段粒度删除），这是所有单文件方案都做不到的。
  • Index 自校验，跨 store 误用与 Index 自身损坏在读之前就被抓住。
  • 共享状态只剩一个「可选的」shm 整数，且正确性不依赖它。

坏处

  • 不支持多进程写 —— 最主要的代价，而且它把问题推给上层。 只有两条路：
    • 专用写入进程 + IPC：append 要跨进程传数据，「返回即持久」的 ack 要跨进程回传，延迟多一跳；
      想保持零拷贝就得上 shm 环 + futex，等于把多进程协调在用户态重新实现一遍。
      1 MB 记录尤其难受：shm 环要么预留到浪费，要么退化成拷贝，而 1 MB memcpy ≈ 100 µs，已与 IO 同量级。
    • 每进程一个 store：可行（目录天然隔离），但跨 store 无序，且上层要自己做路由与合并。
  • 写者是单点。 它死了全局停写。LOCK 由内核自动释放，接管很便宜，但需要外部 supervisor 检测与拉起，
    中间有一段完全不可写的空窗。分片方案里死一个进程，其余 shard 照常服务。
  • CPU 上限收敛到一个进程。 crc32c + 小记录编码 + SQE 填充全压在一处。
    硬件 crc32c ~10-20 GB/s 对单盘绰绰有余，但多盘或几十 GB/s 目标下单核会先于设备饱和。
  • 每批 2 个 IO（.dat + .idx），分片方案是 1 个连续 pwritev。FUA 并发提交所以延迟不叠加，
    但 IOPS 翻倍。批次 ≥ 64 KB 时 IOPS 通常不是瓶颈，小批场景要留意。
  • 引入唯一的原地重写（IdxHeader）。双缓冲 + crc 已化解风险，但它确实是格式里唯一不满足「永不回写」的部分。
  • size_threshold 是个不能改的参数。 写进 STORE、不可变（改了会让旧 Index 的 stream 位失去意义）。
    选错的后果：阈值太高则大记录仍阻塞小记录，太低则小流被中等记录撑大。
  • A8 的概念拆分有认知成本。 「ack 按记录、可见性按前缀」对调用方是两套语义，文档没写清就会被误用。
  • visible_id 可能被一条流拖住。 若大流长时间不提交，小流已 ack 的记录迭代仍看不到（点读不受影响）。
    需要给每条流设最大攒批延迟上限。
  • 独占性只和劝告锁一样硬。 NFS、容器内不同 mount namespace、同进程重复 open 都能绕过。
    LOCK 里的 pid + boot_id + 时间戳只能把误配置变成启动期明确报错。
  • at-least-once 跑不掉（A7）。

选型

  • 「多进程写」是硬需求 → D。E 只是把跨进程协调挪到用户态 IPC，没有消灭它，还附赠一个单点。
  • 写者本来就是一个 daemon，且需要全局总序 + 保留策略 → E。它在这个前提下优于其余四个，没有取舍。
  • 记录大小均匀、批次很小、IOPS 敏感 → D。它每批只有 1 个连续 IO，E 是 2 个。
  • 极简、不需要保留策略、不需要分流 → C。零件最少，可出错表面积最小。
  • 必须多进程、记录彼此独立、无需保留策略 → A。
