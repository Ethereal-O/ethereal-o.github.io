目录形态、多段文件、按 shard 分片，每 shard 单一 I/O owner。崩溃可恢复，支持保留与回收。

  • 并发模型：多进程 · 每进程多线程；独占粒度 = shard，不是 store
  • 记录长度：几 B ~ 1 MB
  • 持久化：O_DIRECT + FUA + 前缀顺序 ack（不使用 fdatasync 作为提交屏障）

相对原始方案的五处改动，全部集中在 §2 与 §4：
① 锁下沉到 shard；② fdatasync → FUA + 前缀 ack；③ committed_end 发布到 shm；
④ 小记录去掉 per-record header/trailer；⑤ checkpoint 与新建 segment 的原子性补齐。
目录布局、Index 自校验、segment 轮转、batch 校验清单这些原设计的核心，一个字没改。

1. API 语义与文件格式

API 契约

append 的返回即代表已持久化。 没有单独的 sync() / flush() —— 返回本身就是持久点。
数据未落盘之前该调用必须阻塞。

不变式
A0 独占粒度是 shard。raf_open 只取到它能抢到的 shard 的写权；一个 shard 同一时刻至多一个写进程。抢不到不阻塞、不排队
A1 append 返回 index ⟹ 该记录已持久；崩溃重启后必定能通过该 index 读到
A2 append 未返回（阻塞中崩溃）⟹ 无任何承诺，该记录通常丢失
A3 append 返回 IO 类错误 ⟹ 该记录是否可见未定义；重试需自带幂等键
A3’ append 返回 EAGAIN（有界队列已满）⟹ 确定性地未写入，可安全原样重试。与 A3 必须是两个错误码
A4 调用期间 buf 必须保持有效且不被修改 —— 实现为零拷贝，IO 直接引用调用方内存
A5 调用不可取消、不可超时返回；一旦进入队列就必须等到终局
A6 顺序：同一 shard 内所有已持久记录有唯一全局顺序，迭代按该顺序返回。跨 shard 无序 —— 迭代是 shard-major 序，与真实时间无关。需要全局序的上层必须自带逻辑时间戳并在读侧归并
A7 迭代是 at-least-once：batch 完整落盘但 committed_end 未及发布时崩溃，恢复后该批变为可见，而 append 从未返回。上层需自带幂等键去重

吞吐的直接后果： 因为 append 阻塞，单个调用线程的吞吐上限 = 1 / 端到端延迟。
要打满设备必须有足够多的并发调用方，由 I/O owner 攒批摊销。
shard_count 是一个伪装成分区参数的并发参数 —— 见 §3 对它的取值讨论。

目录布局

结构

记录编码：分两档（改动 ④）

原设计每条记录都带 header + trailer，粗估 ~20 B。需求里存在几字节的记录，那就是 3-4 倍放大。

档位 编码 完整性由谁保证
小记录（< 阈值，如 4 KB） [varint len][payload]，块内密排 batch_digest 覆盖全批 —— batch 不完整则整批不可见，per-record crc 是重复投保
大记录（≥ 阈值） [RecordHeader][payload][trailer crc] 自身 crc。避免点读时为校验一条 8 MB 记录而必须重算整批 digest

小记录的点读仍然一次 pread 直达：Index.record_offset 指向 payload 起点，record_length 在 index 里，varint 长度只是给迭代用的。

提交有效性（原设计的这一节完全正确，原样保留）

恢复时不能仅凭「找到了 commit magic」就认为提交成功。必须同时确认：

  1. Batch Header 合法（magic + header_crc）
  2. 长度和位置合法（batch_bytes 不越过段尾，first_offset 与前一批衔接）
  3. 所有记录能按长度完整解析，恰好用尽 batch_bytes
  4. Commit Block 的身份与范围一致（store_uuid / segment_uuid / batch_seq / first_offset / batch_bytes）
  5. batch_digest 正确
  6. 与前一个有效 batch 连续衔接（batch_seq 严格 +1）

第 4、5 条是不可省的：data 与 commit block 在设备内部可以被重排，
「commit block 已持久」推不出「records 已持久」。所有原子性来自 digest，不来自写入顺序。

2. 写入与读取流程

写入（改动 ②：fdatasync → FUA + 前缀顺序 ack）

为什么换掉 fdatasync： 它是屏障，拿不到两个同时在飞的持久点，单 shard 提交速率被钉死在 1 / fsync延迟 ≈ 2 万次/秒。于是 shard_count 被迫按吞吐目标选，而 shard 越多每批越小，写放大和 fsync 效率又反过来恶化——两个参数互相对抗。

换成 FUA 之后，持久化语义随每个写命令走，不需要全局屏障，batch k 和 k+1 可以同时在飞。乱序落盘由第 5 步的前缀顺序 ack 兜住：batch 链的前缀持久性由 ack 规则保证，而不是由提交顺序保证。孤儿 batch 不可能出现（batch_seq 不连续即判定为链终点），但设备队列被填满了。

顺带拿回零拷贝：O_DIRECT 不经 page cache，大记录直接从调用方内存 DMA。1 MB 记录省下的 ~100 µs memcpy 已与 IO 同量级。

代价：O_DIRECT 要求 offset / 长度 / 缓冲区按扇区对齐。段头 4 KB 对齐，每批整体补齐到扇区（Padding 本来就存在），块内记录仍然字节紧凑 —— 因为一个 shard 只有一个 I/O owner，同扇区内的排布由它独家决定，不存在两个写者共享扇区。浪费从「每记录 ≤ 4K」降为「每批 ≤ 4K」。

committed_end 的发布（改动 ③）

原设计里 committed_end 活在 writer 的进程内存里，跨进程的 reader 拿不到，读路径第 4 步无法执行。

shm 不存在或已失效（写进程不在）时，reader 退化为「读最新合法 checkpoint」——滞后一个 checkpoint 周期，但永不给出不安全的边界。shm 只是加速，正确性不依赖它。

读取
点读 验 index_checksum → 验 store_uuid → 定位 shard/segment → 取 committed_end → 边界检查 → pread → 校验（小记录靠所在 batch 的 digest 在恢复期已验；大记录验自身 crc）→ 返回
迭代 取 Snapshot { store_uuid, [shard_id, 有序 segment 列表, 各自 committed_end] } → 遍历 shard → segment → batch → record → 产出 (index, payload)
顺序 shard 内严格写入序；跨 shard 无序（A6）

恢复

第 4、6 步合在一起是这个设计最漂亮的地方：撕裂的尾巴原地冻结、永不追加，于是既不需要 truncate，也不存在「新写入落到旧 in-flight IO 落点上」的竞态 —— 那块空间再也没有人会写。前面几个方案里的 GAP_BOUND / 僵尸 IO 宽限期在这里整类消失。

原子性补齐（改动 ⑤）

操作 必须的序列
写 checkpoint 写 checkpoint-<gen+1>.tmp → fsync 文件 → rename → fsync checkpoints/ 目录
新建 segment create + 写 SegmentHeader → fsync 文件 → fsync shard-NNNN/ 目录
checkpoint GC 至少保留 2 个 generation；删除旧的之前确认新的已 fsync

漏掉目录 fsync 的后果是：崩溃后 checkpoint 引用了一个并不存在的 segment 文件。

3. 好处与坏处

好处

  • 放弃「单文件」约束，换来的东西最多。 分段之后：空间可回收、可做保留策略、恢复成本 O(尾部) 而非 O(文件长度)、崩溃不再永久泄漏空间。前几个方案的多数痛苦源于死守单文件。
  • 每 shard 单 I/O owner = N 份「独占单写者」，靠 router 绑在一起。 shard 内无共享 cursor、无锁、天然有序；shard 间零通信。这是调和「要多写者」与「单写者最简单」的干净解法。
  • 锁在 shard 粒度 ⟹ 真正支持多进程写。 各进程持有不相交的 shard 集合，连文件都不共享。
  • FUA + 前缀顺序 ack ⟹ 单 shard 也能 QD > 1。 shard_count 可以按 CPU 核数选，不必按吞吐目标选。
  • committed_end 是一等公民，「已写入」与「已可见」被拆成两个变量，边界检查是单点可审计的，而不是从 crc 链式推导出来的。
  • Index 自校验。 store_uuid + index_checksum 让跨 store 误用和 index 自身损坏在读之前就被抓住；裸 offset 做不到这点。
  • 撕裂尾部原地冻结 + 新建 segment ⟹ 不需要 truncate，不需要任何形式的宽限期或在飞 IO 边界推算。
  • 小记录去掉 per-record header/trailer 后，几字节的记录就只占几字节 + varint。

坏处

  • 跨 shard 无全局顺序，而且补不回来。 shard 之间没有任何同步点，想要全局序只能上层加逻辑时间戳 + 读侧归并。分片的固有代价。
  • shard_count 仍是一个难调的参数。 换掉 fdatasync 后它不再背吞吐 KPI，但仍决定：路由倾斜的严重程度、每批的平均大小、恢复时的并行度、以及文件句柄与内存的占用。选小了单 shard 成为瓶颈，选大了每批太小、写放大上升。
  • 零件多。 STORE / LOCK / segment / checkpoint / shm 五种状态，各有各的原子性要求。任何一处漏 fsync 都是静默损坏，而且只在崩溃后才暴露。实现复杂度低于方案 A，但可出错的表面积最大。
  • O_DIRECT 放弃了 page cache。 读热点需要自己做缓存层，或对读路径单独开一个 buffered fd（写 O_DIRECT / 读 buffered 混用需要注意一致性，通常靠「只读 committed_end 之前的数据」规避）。
  • 独占性只和劝告锁一样硬。 NFS、容器内不同 mount namespace、同进程重复 open 都能绕过。LOCK 文件里应记 pid + boot_id + 启动时间戳，把误配置变成启动期明确报错。
  • at-least-once 跑不掉（A7）：batch 完整落盘但 committed_end 未发布时崩溃，恢复后该批变为可见而 append 从未返回。
  • 写进程崩溃后它那组 shard 的接管需要外部决策。 LOCK 由内核自动释放，接管本身很便宜，但「谁来接」「什么时候接」得有 supervisor。接管前那部分 shard 完全不可写。
  • 每批两次以上的 IO（data + commit block 可合并进一次 pwritev，但段头、checkpoint 是额外 IOPS）。

4. 与前三个方案的对比

A 每进程独立链 B 全局单链 + 锁 C 独占单写者 D 分片多段（本方案）
单文件约束 遵守 遵守 遵守 放弃（关键决策）
多进程写 ✅ ✅ ❌ ✅（LOCK 在 shard 粒度）
共享状态 shm cursor + Slot 表 跨进程锁 + cursor 无 shm 的 committed_end（仅加速，非必需）
单写单元提交 QD > 1 1 > 1 > 1（FUA + 前缀 ack）
并发度来源 进程数 无 QD 分片数 × QD
全局总序 ❌ ✅ ✅ ❌（shard 内有序）
空间回收 / 保留策略 ❌ ❌ ❌ ✅
恢复成本 O(链长) O(链长) O(ckpt 间隔) O(尾部)
崩溃空间泄漏 每次泄漏 每次泄漏 ≤ MAX_INFLIGHT 无（尾部冻结）
在飞 IO 落点竞态 需 GAP_BOUND 需宽限期 需 MAX_INFLIGHT 整类消失
index 自校验 ❌ ❌ ❌ ✅

选型

  • 需要保留策略、空间回收、可运维性 → D。A/B/C 在单文件里做不了这些，而这恰恰是上线后最要命的部分。
  • 需要全局总序 → B 或 C。D 的分片把这件事永久排除了。
  • 极简、写者本来就是一个 daemon → C。零件最少，可出错表面积最小。
  • 必须多进程、记录彼此独立、无需保留策略 → A。

一句话： D 是「无聊但正确」的那一类，也是生产系统真正长出来的形状。上面五处优化只补了它的两个结构性弱点（fdatasync 屏障、锁粒度太粗）和三个工程缺口（跨进程可见性、小记录放大、原子性），核心设计一个字没动。

待定参数：shard_count · 小/大记录阈值 · 批次触发阈值（字节 / 条数 / 时间） · segment 轮转尺寸 · checkpoint 周期 · 队列深度上限
