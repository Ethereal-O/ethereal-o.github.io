单文件。文件由一条全局 MetaUnit 链和大量数据页交错组成。
writer 攒批后构造一个大 MetaUnit，抢全局锁 → 推进全局偏移量 → 写 MetaUnit → 释放锁，随后并行写数据页。

本文对未指定部分的假设（需确认）：页为定长（示例取 64KB），大记录跨页用 FIRST/MIDDLE/LAST 标志切片；锁为跨进程互斥（F_OFD_SETLK 或 shm robust mutex）。

1. API 语义与文件格式

API 契约

append 的返回即代表已持久化。 没有单独的 sync() / flush() —— 返回本身就是持久点。
数据未落盘之前该调用必须阻塞。

不变式
A1 append 返回 index ⟹ 该记录已持久；崩溃重启后必定能通过该 index 读到
A2 append 未返回（阻塞中崩溃）⟹ 无任何承诺，该记录通常丢失
A3 append 返回错误 ⟹ 该记录是否可见未定义；调用方应视为失败，重试需自带幂等键
A4 调用期间 buf 必须保持有效且不被修改 —— 实现为零拷贝，IO 直接引用调用方内存
A5 调用不可取消、不可超时返回；一旦进入队列就必须等到终局
A6 顺序：所有已持久记录有唯一的全局顺序，迭代即按该顺序返回；并发 append 之间谁在前由抢锁决定，未定义
A7 迭代是 at-least-once：可能读到数据完好但 append 从未成功返回的记录，上层需自带幂等键去重

吞吐的直接后果： 因为 append 阻塞，单个调用线程的吞吐上限 = 1 / 端到端延迟。
要打满设备必须有足够多的并发调用方（线程 / 进程），由实现侧攒批摊销 IO 成本。
这条契约也决定了下面格式设计的核心取向：一切结构都服务于「已 ack 的数据绝不可丢」。

布局

结构

三条格式铁律

  • F1 数据页零元数据。 校验与长度全部在 MetaUnit 的 Entry 里，页内不留任何头部。
  • F2 页按扇区对齐分配。 扇区是写入的最小单位，两个进程共享扇区必然互相覆盖；页内部完全不对齐。
  • F3 永不回写任何字节。 写 MetaUnit#N 之前，在锁内先把 #N+1 的位置预留掉，链始终向前声明。

2. 写入与读取流程

写入

不变式 L1：锁必须持有到 MetaUnit 持久，不能在提交后就释放。
否则两个 MetaUnit 同时在飞，后者先落盘、前者没落，链上出现无法到达的孤儿单元 —— 其中已 ack 的记录将永久丢失。
锁”持有到持久”正是本方案正确性的来源：它自动保证了链的前缀持久性。

不变式 L2：ack ⟺ meta 与 data 均持久。 崩溃时仍在队列、在锁外排队或在飞的记录一律丢失 —— 它们从未 ack。

可做的优化： 第 3 步里数据页的分配可以移到锁外（单独的原子 fetch_add），第 6 步的数据写与第 4 步的 meta 写并发发出。延迟从 2 × IO 降到 1 × IO，锁的持有时间不变。

读取与恢复
点读 index → 读对应页 → 验 data_crc → 跳到页内偏移。一次 IO。
迭代 走链 → 每个 Entry 读其页区间 → 页内 varint walk。顺序即全局写入顺序。
恢复 读 SuperBlock → 从 Meta#0 沿 next_offset 走，见第一个无效 MetaUnit 即停（链不可能有洞）→ 逐 Entry 验数据 crc，不过即为从未 ack，跳过 → cursor = 已知最大 offset + 安全边距。

恢复从不扫描数据区：不需要 magic 搜索、resync 启发式或误判概率论证。

3. 好处与坏处

好处

  • 全局写入顺序天然成立。 迭代是一条链的线性遍历，顺序就是真实写入顺序，不需要逻辑时间戳或读侧归并。
  • 恢复是最简形态：走一条链，见坏即停。不扫数据区，不需要跨过空洞。
  • 锁自动保证链的前缀持久，不会出现孤儿 MetaUnit，也不需要”按链序释放 ack”的记账逻辑。
  • 文件级元数据只有 SuperBlock：没有 slot 表、没有槽位耗尽、不必为槽位滚动 segment。
  • cursor 在锁保护下，连原子操作都不需要，也不依赖共享内存存活。
  • 永不回写 ⟹ 已 ack 的数据不可能被任何后续写破坏。

坏处

  • 锁跨 IO 持有 ⟹ meta 的队列深度恒为 1。 全局 meta 吞吐上限 = 1 / IO延迟 ≈ 2 万次/秒。
  • 尾延迟 = 进程数 × meta IO 延迟。 64 进程 × 50µs ≈ 3.2 ms。
  • 延迟与吞吐被锁绑死。 想降延迟就得缩小批次，缩小批次就加剧锁争用 —— 两头不可兼得。这是本方案最本质的限制。
  • 一个进程慢或卡住，所有 writer 一起等。 持锁进程崩溃需要锁能自动释放（F_OFD_SETLK 可以，普通 mutex 需要 robust 语义）。
  • 持锁者崩溃后的 next_offset 重写竞态： 它预留的下一个 MetaUnit 位置必须由后继者写入，而死进程可能仍有在飞的 IO 指向那里。单链下无法靠”换个位置”规避，只能加宽限期。
  • 低负载写放大： 只有几条记录也要写出一个完整的 MetaUnit。
  • 为全局顺序付了全局锁的代价。 如果记录之间本就独立，这笔开销是白花的。
  • meta 先于 data 的串行顺序会让延迟翻倍（可按 §2 的优化改为并发）。

4. 与「每进程独立链」方案的对比

B：全局单链 + 锁 A：每进程独立链
全局写入顺序 天然具备 无，需逻辑时间戳 + 读侧归并
meta 并发度 QD = 1 不受限
尾延迟 进程数 × IO 1 × IO
文件级元数据 仅 SuperBlock 额外 Slot 表，且会耗尽
链的前缀持久 锁自动保证 需进程内按链序释放 ack
慢进程的影响 阻塞所有人 只影响自己
恢复 走 1 条链 并行走 N 条链
崩溃后的位置重写竞态 存在，需宽限期 换新槽位即可规避
实现复杂度 更低 更高

选型建议

  • 需要全局写入顺序 → 选 B。锁买到的就是这个，其余都是代价。
  • 记录彼此独立 → 选 A。B 的锁是纯损失。
  • 两者都要 → 折中方案：全局锁只保护「排序 + 分配」（纳秒级，不跨 IO），MetaUnit 内容推进共享 ring，由一个 leader 批量写出。保留全局顺序，同时把 meta 的 QD 从 1 放开。代价是引入共享缓冲区和一次拷贝（每条 Entry 约 20B，可忽略），以及 leader 的故障转移。

待定参数：page_size · meta_unit_size · 攒批触发阈值 · 安全边距 · 持锁者崩溃后的宽限期
