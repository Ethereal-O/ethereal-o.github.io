单文件、同一时刻只允许一个 writer 进程打开（第二个 open 直接报错），崩溃可恢复。
写入返回 index，支持按 index 点读与顺序迭代。reader 不受限，可多进程只读并发。

  • 并发模型：单进程 · 多线程；进程级独占由 F_OFD_SETLK / flock 保证
  • 记录长度：几 B ~ 1 MB
  • 持久化：O_DIRECT + FUA

本方案的出发点：独占不是”砍掉一个功能”，而是把整个跨进程协调层删掉。
换来的能力比方案 B 的全局锁能买到的更多 —— 尤其是「全局总序」与「队列深度 > 1」同时成立。

1. API 语义与文件格式

API 契约

append 的返回即代表已持久化。 没有单独的 sync() / flush() —— 返回本身就是持久点。
数据未落盘之前该调用必须阻塞。

不变式
A0 同一文件同一时刻至多一个 writer。raf_open 拿不到独占锁即失败，不阻塞、不排队，由上层决定重试或退出
A1 append 返回 index ⟹ 该记录已持久；崩溃重启后必定能通过该 index 读到
A2 append 未返回（阻塞中崩溃）⟹ 无任何承诺，该记录通常丢失
A3 append 返回错误 ⟹ 该记录是否可见未定义；调用方应视为失败，重试需自带幂等键
A4 调用期间 buf 必须保持有效且不被修改 —— 实现为零拷贝，IO 直接引用调用方内存
A5 调用不可取消、不可超时返回；一旦进入队列就必须等到终局
A6 顺序：所有已持久记录有唯一的全局顺序，迭代即按该顺序返回；并发 append 之间谁在前由入队顺序决定，未定义
A7 迭代是 at-least-once：可能读到数据完好但 append 从未成功返回的记录，上层需自带幂等键去重

吞吐的直接后果： 因为 append 阻塞，单个调用线程的吞吐上限 = 1 / 端到端延迟。
要打满设备必须有足够多的并发调用线程，由实现侧攒批摊销 IO 成本。
本方案的全部结构都服务于两句话：已 ack 的数据绝不可丢，且ack 不需要等待队列排空。

布局

结构

格式铁律

  • F1 数据区零元数据。 所有描述信息都在 MetaUnit 里。恢复从不扫描数据区，空洞是纯空间泄漏，不影响正确性。
  • F2 永不回写任何字节。 写 MetaUnit#N 前先预留 #N+1 的位置，链始终向前声明，不存在回填指针。
  • F3 header_crc 与 body_crc 分开。 body 撕裂时 unit_seq / next_offset 仍然可信，可判定”本单元是撕裂的终点”而非乱跳。
  • F4 对齐只发生在批次边界。 单写者意味着同一扇区内的排布由唯一一个进程决定，不存在”两个进程共享扇区互相覆盖”。
    于是浪费从「每条记录 ≤ 4K」降为「每批 flush ≤ 4K」，攒批后趋近于零 —— 几字节的记录就真的只占几字节。

Checkpoint 是本设计中唯一被原地重写的区域，因此做成双缓冲 + crc：
任一份撕裂都不影响另一份，恢复永远能拿到一个合法起跳点。

2. 写入与读取流程

打开

  1. open + F_OFD_SETLK 取整文件写锁。拿不到 ⟹ 立即 EBUSY（A0）。
  2. 执行恢复（见下），得到 cursor / last_unit_seq / last_record_id。
  3. 写入 owner_hint。锁是劝告性的，这条记录不防恶意，只把”误配置导致的静默损坏”变成启动时的明确报错。

写入

  1. 写线程把 WriteReq（栈上）push 进本地 MPSC 队列（一次 XCHG），阻塞在 futex。
  2. leader 摘下一批：小记录 memcpy 进 chunk buffer 密排，大记录直接挂 iovec 零拷贝，计算 data_crc。
  3. 本地 cursor 连续切三块：DataChunk、本 MetaUnit、下一个 MetaUnit（预留）。整批尾部补齐 4K。
    cursor 只被 leader 线程访问，连原子操作都不需要。
  4. io_uring 并发提交 DataChunk + MetaUnit，均带 FUA。不等 CQE，直接回去收割下一批。
  5. CQE 回来后按 unit_seq 前缀顺序 ack：seq = k 的唤醒必须等所有 < k 的单元都已持久。
  6. 每 N 个单元或 T 毫秒，轮换写一次 Checkpoint（FUA）。它不在 ack 路径上，慢了只影响恢复时间。

第 4、5 步是本方案的核心。
方案 B 为了避免”后一个 MetaUnit 落盘、前一个没落 ⟹ 孤儿单元 ⟹ 已 ack 数据永久丢失”，
必须把锁持有到 MetaUnit 持久，代价是 meta 的队列深度恒为 1。
这里换了个解法：乱序提交、前缀顺序 ack。链的前缀持久性由 ack 规则保证，而不是由提交顺序保证。
孤儿单元同样不可能出现，但设备队列被填满了。
这个做法在多进程下做不到（需要跨进程排序），单写者下它只是一个本地环形缓冲区。

读取
点读 index → 一次 pread 取 DataChunk → 验 data_crc → 跳到块内偏移。一次 IO，零内存索引。
迭代 从 Checkpoint 或链头走链 → 每个 Entry 读一块 → 块内 varint walk 逐条产出。顺序即全局顺序。
reader 并发 reader 只读，不需要锁。看到的是一个移动的前沿，重新走链即可推进。

恢复

  1. 读两个 Checkpoint，取 crc 合法且 ckpt_seq 更大者。两个都坏 ⟹ 从链头走（退化，正确性不受影响）。
  2. 从 last_unit_offset 顺链前进，直到 header_crc 失败、body_crc 失败或 unit_seq 不连续 —— 那里就是链的终点。
  3. 逐 Entry 验 data_crc，不过即为从未 ack，跳过。
  4. cursor = max(chain_end, checkpoint.high_water) + MAX_INFLIGHT_BYTES
  5. 从 last_seq + 1 继续写。

恢复时间从 O(文件长度) 降为 O(checkpoint 间隔)。 固定位置的 Checkpoint 之所以安全，正是因为没有并发更新者。

两个必须讲清的点

僵尸 IO。 独占锁在进程死亡时由内核自动释放，但它已经交给块层的写可能在锁释放之后才落盘，落点最远到它已分配的 cursor。新写者无从得知那个值，所以 Checkpoint 里额外记 high_water（已分配水位，不是已写水位），恢复时按上面的公式跳过一段。

MAX_INFLIGHT_BYTES 是写者自己的在飞上限（如 64 MB），一个静态常量 —— 不需要任何存活检测。代价是每次崩溃泄漏 ≤ 该常量的空间。这是方案 A 里 GAP_BOUND 的同一个招，但单写者下它是确定的常量，而不是「槽数 × 每进程上限」。

残留单元不会造成幽灵链。 上一次崩溃可能在链断点之后留下了看起来合法的 MetaUnit。但 unit_seq 与位置由链严格绑定：若上一轮在偏移 X 写下的 seq = P+1 曾经持久且合法，恢复就会跟进去；恢复停在 X 说明那里的单元本就无效。新写者在 X 重写自己的 P+1，crc + seq 连续性两道检查足以排除更早轮次遗留的、序号更大的越位单元。

3. 好处与坏处

好处

  • 共享状态归零。 跨进程协调层整体消失：无 shm cursor、无 slot 表与槽位耗尽、无跨进程锁、无死活检测。
  • 全局总序是白送的。 单链 + 单分配者，unit_seq 即全局顺序。方案 B 花一把跨进程锁买到的语义，这里是副产品。
  • 总序与 QD > 1 同时成立。 前缀顺序 ack 让 meta 可以流水线化，而方案 B 的锁把 meta 的 QD 压死在 1。这是本方案相对 B 的决定性优势。
  • 对齐浪费降到每批 ≤ 4K。 同一扇区不再被多个进程共享，块内可字节紧凑排布。
  • 恢复是有界的。 双缓冲 Checkpoint 起跳，不必走完整条链，也从不扫描数据区。
  • 快路径上连原子操作都没有。 零拷贝，大记录直接从调用方内存 DMA。
  • 永不回写（Checkpoint 除外，且双缓冲）⟹ 已 ack 的数据不可能被任何后续写破坏。
  • 实现复杂度显著低于 A 和 B：没有一样东西是为了跨进程正确性而存在的。

坏处

  • 不支持多进程写入 —— 这是最主要的代价，并且它把问题推给了上层。 只有两条路：
    • 专用写入进程 + IPC：每次 append 要跨进程传数据。走 socket 有一次拷贝 + 两次上下文切换，且「返回即持久」的 ack 要跨进程回传，延迟多一跳。想保持零拷贝就得上 shm 环 + futex —— 那等于把方案 A 的跨进程协调在用户态重新实现了一遍。1 MB 的大记录尤其难受：shm 环要么预留到浪费，要么退化成拷贝，而 1 MB memcpy ≈ 100 µs，已与 IO 同量级。
    • 每进程一个文件：与「单文件」约束直接冲突，出局。
  • 写者是单点。 它死了全局停写。OFD 锁自动释放使接管本身很便宜（新进程 open 即可），但需要外部 supervisor 做检测与拉起，中间有一段完全不可写的空窗。方案 A 里死一个进程，其他进程毫无感知地继续写。
  • CPU 上限收敛到一个进程。 crc32c + 小记录 memcpy + SQE 填充全压在一处。硬件 crc32c ~10–20 GB/s、memcpy ~10 GB/s，对单盘绰绰有余；但若目标是多盘并发或几十 GB/s，单核会先于设备饱和。
  • 独占性只和劝告锁一样硬。 NFS、容器内不同 mount namespace、以及”同一进程把文件 open 两次”都能绕过。owner_hint 只能把误配置变成明确报错，不能真正阻止。
  • 引入了唯一的原地重写区域（Checkpoint）。已用双缓冲 + crc 消除风险，但它确实是格式里唯一不满足「永不回写」的部分。
  • 每次崩溃泄漏 ≤ MAX_INFLIGHT_BYTES。 换来的是不需要任何存活检测。
  • 每次 flush 两个 IO（并发发出，延迟不叠加，但 IOPS 翻倍）。
  • at-least-once：迭代可能看到数据完好但从未 ack 的记录，上层需自带幂等键。

选型建议

  • 「多进程写同一个文件」是真需求 → C 只是把复杂度从文件格式挪到了用户态 IPC，并没有消灭它，还附赠一个单点。选 A 或 B。
  • 需要全局总序，且写者本来就是一个 daemon → 选 C。它在正确性、性能、实现复杂度三个维度同时优于 A 和 B，没有取舍 —— 尤其是它同时拿到了全局总序和 QD > 1，而 B 为了总序把 QD 压死了。
  • 需要全局总序，但必须多进程写 → 选 B，或 B 的折中版（锁只保护「排序 + 分配」这段纳秒级临界区，不跨 IO；MetaUnit 内容推进共享 ring 由 leader 批量写出）。
  • 记录彼此独立、无需总序、必须多进程写 → 选 A。

待定参数：meta_unit_size · flush 触发阈值 · Checkpoint 间隔（N 个单元 / T 毫秒） · MAX_INFLIGHT_BYTES
