9.24 Design Doc

整理自 stage3.md（2026-09-30），共 14 页。

0. 背景

需要设计一个 RAF 存储系统，核心目的是：

  1. 向用户提供持久化语义，用户能够根据 API 完成随机读、顺序读和顺序写。
  2. 在单次 record size 为 4k 和 1M 的时候，拥有比较好的顺序读性能。
  3. 从单个 reader/writer 扩展到多个的时候，拥有比较好的扩展性。

1. 层级

整体架构可以分成三级，三级尽量解耦设计。

1.1 Frontend

这层的目的：

  • 对接 API，提供用户层语义
  • 提供多线程/多进程一致性保障，向下层过滤掉多线程多进程导致的安全问题

1.2 Middle

这层目的：

  • 提供文件层语义，包括文件格式，RAF 真正的文件设计

1.3 Backend

这层目的：

  • 后端接口，posix / io_uring / spdk 等

2. Frontend: API 语义

2.1 返回语义

返回语义可以有几种选项：

  • 返回即代表持久化；
  • 返回不代表持久化，持久化时间随机；

如果返回不代表持久化，虽然可以额外增加查询是否持久化的接口，但是对下游的语义修改是比较大的。所以应该采用返回即代表持久化语义。

2.2 Index 语义

Index 有几种选项：

  • Int 当前默认设计
  • 用一个复合的结构体

用复合的结构体优点是：

  • 能存储更多信息
  • 能直观表示细节

缺点是：

  • 占用额外的空间
  • 后续设计可能需要考虑它本身的 cache line 对齐等优化

对于一个文件的格式来说，Index 直接对应偏移量是足够的，并且我们没有必要向下层表示更多细节，所以用 int 就可以。

2.3 迭代读语义

迭代读语义取决于不同的设计。可以是要求全局一致（每个 Reader 读的顺序一致），也可以不一致。

2.4 接口

失败定义：

  • 用户执行操作导致的：抛出 std::logic_error
  • 系统故障导致的：抛出 std::system_error

3. Frontend: 多进程/多线程适配

3.1 多线程/多进程

为了适配用户语义上的多线程/多进程，有几种方案：

  1. 唯一写者。所有的 Writer 将写请求发送给这个中心化写者，由它来做统筹写入。
  2. 多个写者同时写入：
    • 同时写入数据
    • 同时写入元数据

3.1.1 中心化写者

整体架构设计只有一个中心化写者，而无论多进程还是多线程，都是 Writer 对象只需要给这个写者发送任务即可。也就是说，这里会有一个 MPSC 队列。

Writer 会向中心化写者注册，因此中心化写者知道有多少 Writer。中心化写者会进行攒批，当计时器结束或者没有可用的 Writer，或者到达批次上限时候会向 Middle 写入 batch 数据。完成之后回调并释放 Writer。

  • 需要注意的是，中心化写者不一定只有一个 IO 线程，它可以有多个线程，使得 CPU 提交侧不是瓶颈。（默认先关闭）
  • Reader 自己持有自己的队列，可以攒批触发，也可以不攒批。（先实现成不攒批的，后续看情况决定）

中心化写者的位置设计和性能关系是：

  1. 如果只有一个 Writer，那么因为 Writer 请求间是串行的，所以严格和延迟相关。因此，我们必须缩短在单个 Writer 下的路径。
  2. 如果有多个 Writer，带宽大概率只和中心化写者的配置有关，因为上游的 MPSC 队列等可以通过其他优化来解决。

Writer 需要发送给中心化节点，可能会增加一次拷贝。但是这种情况一定是多个 Writer，因为单个 Writer 自己就是这个中心化写者。而多个 Writer 的性能可能大概率与拷贝关系不大。

综上，中心化写者只需要跟随第一个 Writer 即可。

在多线程模式下，程序出现异常所有 Writer 都会失败，因此中心化写者不需要考虑所有权转移。

在多进程模式下，会出现单个 Writer 崩溃而其他 Writer 存活的可能性，因此需要考虑中心化写者的所有权转移问题。也就是说，当第一个 Writer 进程启动并且它是中心化写者，第二个 Writer 将会给第一个进程的共享内存发送内容。而第一个 Writer 结束运行或者失败后，第二个 Writer 应该立即能接管所有权运行。

那么可行的比较简单的方案就是通过 flock 做任期管理。关键在于恢复和接管。注意到我们的 API 语义是返回即代表持久化，而不返回的信息可以丢失。所以如果这时候崩溃，那么队列中的内容是允许丢失的。

所以，提交的顺序就可以是：

  1. 将 Writer 可用数目减一
  2. 如果是 0，并且队列长度是 0，那么直接提交
  3. 否则要多 Writer，从队列 pop 出一个或一批
  4. 将这块写入
  5. 原子更新共享内存中的全局文件尾部

当 3 步结束或者中间某一时刻崩溃时，由于 API 接口尚未返回，API 语义保证了没有意外的数据丢失。当第 4 步中间丢失，全局 size 尚未增加，因此直接覆盖，认为这一批全部丢失。

而接管的步骤是：

  1. 提交当前的内容到共享队列中
  2. 等待。定时检查一下 flock，如果拿不到锁，证明有人在任期，放弃。否则立即成为 Leader。
  3. 接管成功后，从原子更新的全局文件尾部开始处理。

中心化写者的优点是：

  1. 拥有全局的顺序，不需要考虑 Consistency Order。保证不同 Reader 拿到的顺序是一致的。
  2. 中心节点可以决定攒批和真正的 IO 线程数目，减少 Writer 过多导致的锁竞争问题。

缺点是：

  1. 多个 Writer 有拷贝开销

3.1.2 多个写者同时写入数据

这个方案每一个 Writer 尝试写入包含以下步骤：

  1. 先获取 flock 锁
  2. 写入 Meta，扩展文件
  3. 释放锁
  4. 写入数据

优点是：

  1. 比较简单
  2. 拥有全局的顺序，不需要考虑 Consistency Order。保证不同 Reader 拿到的顺序是一致的。
  3. 即使是多个 Writer，也没有拷贝开销

缺点是：

  1. 无法攒批和分线程。
  2. 单个 Writer 也需要获取全局 flock 锁，否则后续注册的 Writer 可能会写入。
  3. 如果支持并行写数据，那么就很可能留下空洞，同时可能会有放大的问题。如果不支持并行写，那么就变成了严格串行。
  4. 因为语义规定，API 返回之后保证持久化。所以当恢复确定 Writer 写前沿的时候，读到错误的数据，还需要接着往后读，直到读到最后。迭代也是同理。
  5. Writer 足够多的时候可能会随机写。

3.1.3 同时写入元数据

同时写入元数据要配合 Middle 层做调整，也就是下面提到的链式方案。

优点是：

  1. 写入位置灵活。通过指针连接已对齐的 chunk，不要求记录在物理文件中连续存放。

缺点是：

  1. 复杂
  2. 没有全局顺序，不同 Reader 有可能拿到不同的顺序
  3. 读放大
  4. 空间浪费

3.1.4 同时写入数据 V2

基于同时写入数据的版本。

我们可以针对每个 Writer，让其拥有一段独占的区域（这里有不同方案，可以是单个文件内的区域，也可以是每个 Writer 独占整个文件）。Writer 直接在这段区域里面写入。

考虑到空洞以及单文件管理问题，可以使用多文件。

Writer 初始化顺序：

  1. 遍历文件，通过 flock 找到一个当前没有占用的文件或创建新文件（O_CREAT | O_EXCL），加锁。（理论上应该是 middle 层提供一个加锁 API）
  2. 遍历这个文件，验证并找到最后一个安全的点。

Writer 写入顺序：

  1. 根据 middle 层，写入一块内容。
  2. 检查距离上次检查了多久，如果过了很久，那么就看看有没有文件损坏标记。如果文件损坏，那么就新开一个文件。

Reader 迭代读顺序：

  1. 获取所有文件尾部并记录。
  2. 归并排序，读最早的。这里通过预取获得文件的排序依据（时间戳）。
  3. 获取某个文件的下一个。如果补充不到，说明文件要么读完，要么已经损坏，不再预取 meta。（middle 层返回损坏或读完）
  4. 直到所有文件读到超过尾部那么就不读了（下一条的起始点小于等于，结束点大于，或读不到下一条），尝试看看之前的文件有没有更新，也就是更新尾部记录，并且重新读（以防漏掉正在写的）。

预取的形式如下（由 middle 层负责）：

  1. 对于每个文件，初始化的时候，预取 meta1，此时队列为 [meta1]。
  2. 当触发读请求时：
    • 如果文件确认整体损坏，不再读。
    • 如果队列为空，那么尝试补足 meta。如果补足失败，那么还没有写入，到文件末尾。如果成功，这时候队列为 [meta1]。
    • 校验 meta1 crc，如果没通过，检查文件长度。如果文件长度超过 p + meta_len + max_data_len + meta_len，那就记录成从这里开始损坏。否则认为还没有写入，到文件末尾，将 meta1 释放回去。
    • 尝试一次性取 data1 + meta2。
      • 如果取完了 meta2，此时队列为 [meta1, data1, meta2]
        • 验证 [meta1, data1]。如果失败，表示部分损坏，pop1，并且再次触发读请求。否则成功返回 1。
      • 如果只取完了 data1，那么此时队列为 [meta1, data1]
        • 验证 [meta1, data1]。如果失败，表示到文件末尾，将 data1 释放回去。否则成功返回 1。
      • 如果连 data1 也没有取完，那么还没有写入，到文件末尾。

迭代读能够保证的语义是：

  1. 如果两个 reader 在 open() 时取得相同的完整尾部向量（每个文件的已完成写入尾部相同），那么它们对于这些尾部向量之前的 readNext() 会返回相同的记录和顺序。也就是说，如果两个 reader 打开的间隔中间没有写，那么对于它们打开之前的写，返回的顺序一致。
  2. 如果已经打开 reader，对于它们的尾部向量后面的元素，只能保证相同文件的顺序性。也就是说，对于后续的写，保证的语义是相同 writer 的顺序一致，而不同 writer 的读取顺序不能保证。

例如，对于全局顺序：

对于 W1:1 W2:1 W1:2 W2:2，两个 reader 获得的顺序是一样的，都是 W1:1 W2:1 W1:2 W2:2。而对于 W1:3 W2:3 W1:4 W2:4，两者的顺序可能不一致，R1 可能读到 W1:3 W2:3 W1:4 W2:4，而 R2 可能读到 W1:1 W2:1 W2:2 W1:2。但是，对于 W1 和 W2 内部，顺序是一致的。

Reader 随机读顺序：

  1. Index 这时候不但要包含位置，还需要包含文件 id。可以用 int 的高位代表文件 id，低位代表文件内偏移量。这是因为可以控制每个文件最大的尺寸。例如单个文件不能超过 256TB（2^48），而高的 16 位可以存放 65536 个文件，允许 65536 个 Writer 同时打开。

优点是：

  1. 比较简单
  2. 即使是多个 Writer，也没有拷贝开销

缺点是：

  1. 没有拥有全局的顺序。

4. Middle: 文件格式

4.1 Record 模式

Block 分为几种：Meta Block、Data Block。

每个 chunk，写入一个 Metadata Block，表明 Length + 时间戳 + meta crc + 全部 crc，然后写数据，里面有结束标记和 CRC。

由于 meta block 和 data block 一定是一起出现的，所以是一起写入的（一个写请求），并且是通过 O_DSYNC 写入。如果返回，那么就能够代表其已经持久化。需要注意的是都被一起提交到队列中，但是不代表是原子的。

读取时，根据 Length 去读，如果 CRC 校验通过，那么就读成功。

迭代根据 Length 进行，而随机读根据文件内偏移量进行。

为了保证正确性，我们先让每次都校验 crc。设计结束后看着性能，只有重复读同一批记录很常见、且 CRC 或磁盘读取确实成为瓶颈时，再考虑 RAF 自己的 LRU 优化。

优点：

  1. 一个文件同时存元数据和数据，保证全局顺序
  2. 只 Append，性能比较好
  3. 设计实现比较简单

缺点：

  1. 统一设计，不利于扩展多写情况。
  2. 额外的空间占用，没有对齐的数据都可能导致写放大。

4.2 分离式

index 文件和 Data 文件分离。写入文件的时候先写 data 文件，写完后再写 index 文件，index 文件后同样有 CRC。

优点：

  1. 设计比较简单
  2. 额外空间占用比较少

缺点：

  1. 写入需要写两个文件，性能可能会比较差
  2. 两个文件都需要保证正确性

4.3 链式

提前确定好每个 chunk 的大小，让数据都对齐。当写入时，提前先锁定一块用于存放 Meta-B，然后锁定一块用于存放 Data-A，先写数据，然后利用之前锁定的 Meta-A 写入数据位置、下一块 Meta 区域、DataLength、CRC。

优点：

  1. 可以支持多写者并发调用（但是目前证明多写者是不好的）

缺点：

  1. 比较复杂
  2. 分离设计，性能可能比较差

4.4 最终选型

计划选 Record 格式的，因为它性能比较好。

5. Backend: 写磁盘

计划先采用 io_uring。虽然 io_uring 有很多问题，但是可以后续再调整。

6. 测试内容

  • API 契约、持久化契约：覆盖创建、打开、追加、读取、关闭的正常调用和非法调用顺序，检查返回值及状态变化。分到验证写入成功返回、同步成功返回的持久化保证，以及写入尚未返回时缺漏后的允许结果；若创建新文件也在保证范围内，还要验证目录项的持久化。
  • 预期错误与故障注入：主动制造无效参数、重复打开写者、权限不足、空间耗尽、短写、同步失败和数据损坏，检查错误码与后续状态。重点确认失败不会让记录被误判为完整，也不会使后续写入永久卡住。
  • 边界条件与长度溢出：测试空记录、最小和最大记录、批次边界、块边界、文件末尾，以及恰好超出限制的长度。对长度相加、偏移计算和空间预留构造数值溢出输入，确认在分配或写盘前拒绝。
  • 正确性对照测试：测试程序为每条写入生成唯一 ID、内容校验值和调用时间线，将 RAF 读出结果与契约允许的结果自动比较。并发和崩溃测试可以更换随机种子反复运行，失败时保留种子与故障注入点以便复现。
  • 崩溃恢复与并发崩溃恢复：在预留位置、写数据、写元数据、同步和返回确认等阶段分别终止进程，重开后检查完整记录集合与恢复位置。对多个在途写入重复此测试，确认已承诺持久化的记录不丢失，未完成记录不被当作完整记录。每次恢复后立即追加新记录，再次关闭和重开；检查新记录没有覆盖旧记录，索引、长度和下一写入位置一致。
  • 并发正确性与反复开关：用多线程、多进程的 writer 和 reader 交错运行，被对记录无重复、无串扰、内容完整，且读取顺序符合已定义的契约。并发执行打开、关闭、崩溃和重开，检查 writer 互斥、资源释放，以及 reader 对新记录的可见性。
  • 性能测试：用目标业务负载分别测吞吐、恢复耗时和资源占用。
  • 压力测试：增大 writer 和 reader 数目，检查性能变化情况。

7. 计划推进顺序

  1. 实现 backend，做好底层文件是否成功写入的功能单元测试
  2. 实现 middle 层，做好功能和单元测试
  3. 实现单 Writer 写入数据，验证 API 语义测试、边界条件测试、故障处理、崩溃恢复、正确性对照测试
  4. 扩展到多线程，验证并发正确性和反复开关下的正确性
  5. 进行性能测试
  6. 验证多进程
