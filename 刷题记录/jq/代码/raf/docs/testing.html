What the suite tests, and what each test is for

There are two. raf_core_test is 24 tests in one file, under two seconds,
holding the properties raf would be broken without –
tests/core/README.md says what it leaves out and shows which deliberate
breakages it does and does not catch. raf_test, described below, is the
whole thing: 164 tests, and the one to run before shipping.

164 tests in 14 files, one binary (raf_test) – 173 when the io_uring
backend is built in, because the IO-layer tests run once per backend. Every
one of them is deterministic: payloads are a pure function of (writer, sequence, size) and
every rendezvous between threads or processes is a std::latch or a pipe, so
a failure reproduces. Nothing sleeps and nothing is random.

test_faults.cpp — injected failures

Everything raf does to a file goes through IoBackend, so that is where a
failure can be injected the filesystem will not produce on demand.
tests/fault_backend.h holds a ForwardingBackend that passes everything
through and a FaultBackend with four knobs: how many writes to let past
before bending one, how many bytes of the bent write land before it reports
EIO, an offset to fail writes at, and whether fsync fails. It also records
syncDirectory calls, which is the only way to assert on one — the
durability of a new segment’s directory entry leaves no trace in the archive.

These drive the store layer directly, since that is the level a backend is
injectable at.

test_direct.cpp — the O_DIRECT read path and the window

O_DIRECT is what Options::directReads asks for and it is on by default:
no page cache, and three alignment rules — offset, length and buffer address
all multiples of the device’s logical block. Everything the buffered reader
promises has to survive that, which is why the buffered side is still here
to compare against.

Because the default is O_DIRECT, every test in the suite needs a
filesystem that can do it. TempArchive picks one, falling back from /tmp
to the working directory, since tmpfs refuses O_DIRECT outright.

Equivalence — Segment::readPayload with direct_ set, via
src/store/read_window.cpp:

Bytes moved — these are the only tests in the suite that count what the

What the suite does not test

Deliberately, and measured elsewhere:

  • Performance. No test asserts a rate. The two byte-counting tests in
    test_direct.cpp are the exception that proves it — they assert bytes
    requested    , which is deterministic, not time. Throughput lives in
    bench/ and the numbers in docs/performance.md.
  • Resource use. Now reported by the benchmarks rather than asserted:
    raf_bench prints a CPU-seconds-per-GiB column and a peak-RSS line,
    raf_matrix carries both on the end of its report line.
  • Real power loss. SIGKILL and truncation stand in for it. They cover
    a process dying, not a drive that lies about its cache.
  • Filesystems that cannot do O_DIRECT. Options::directReads can be
    turned off for them, but the suite exercises the default and so needs a
    root that supports it.

Against the design doc

docs/stage3.md §6 lists eight kinds of test. Where each one landed:

stage3 §6 here
API 契约、持久化契约 test_api.cpp, with RecordsAreOnDiskBeforeAppendReturns for the returning-append-is-durable promise and ANewSegmentSyncsTheDirectoryItWasCreatedIn for the directory entry
预期错误与故障注入 test_errors.cpp for the failures a real filesystem produces, test_faults.cpp for the ones it will not
边界条件与长度溢出 test_boundary.cpp, including the three overflow tests
正确性对照测试 test_support.h‘s PayloadId — every record carries its writer, sequence and a checksum
崩溃恢复与并发崩溃恢复 test_recovery.cpp
并发正确性与反复开关 test_concurrency.cpp, test_multiprocess.cpp
性能测试（吞吐、恢复耗时、资源占用） bench/; recovery scan time and the CPU/RSS columns are both in raf_bench
压力测试 test_stress.cpp, and bench/physical/vsfio.sh from 1 to 256 workers

Two places where the implementation deliberately differs from what §6 asks
for, both because the result is stronger:

Seeds. §6 suggests re-running the concurrency and crash tests with
different random seeds and keeping the seed of a failure to reproduce it.
There are no seeds here. Payloads are a pure function of
(writer, sequence, size) and every rendezvous is a std::latch, so there
is nothing to keep — a failure reproduces because the inputs never varied.
What varies between runs is the interleaving, and no assertion depends on it.

Crash points. §6 asks for the process to be killed at five named stages:
after reserving, after writing data, after writing metadata, after syncing,
and after acknowledging. AFileCutAtAnyPointRecoversToARecordBoundary
truncates at every byte offset instead. The on-disk states those five
stages produce are a subset of what it covers.

The benchmarks, for contrast

Not part of raf_test; these are scripts that need a machine and a drive.
Each answers a question rather than producing a score.

script the question
bench/physical/vsfio.sh how close is raf to fio in the same shape, 1→256 workers, six workloads
bench/physical/seqscale.sh does that still hold once the device is saturated — every worker on its own stream, four matched sides per point
bench/physical/ceiling.sh what can this drive actually do, and how much of it can a synchronous buffered reader reach
bench/physical/appendscale.sh why durable append stops scaling at sixteen writers; takes the append path apart variant by variant
bench/physical/appendcost.sh where the microseconds in one durable append go
bench/physical/sustained.sh where the drive’s SLC cache runs out, and whether batching survives the cliff
bench/physical/diagnose.sh is this drive healthy enough to trust a run on it
bench/physical/run.sh all of the above into one results file
bench/raf_matrix.cpp the harness: write, scan, read, seqread, odread, odrand, with device-level amplification from /proc/diskstats
bench/bench_raf.cpp the standalone benchmark, no fio and no root needed

which are still open; docs/performance.md is where the answers are.
