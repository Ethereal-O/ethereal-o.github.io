HGI 场景测试报告

测试日期：2026-10-04
整理日期：2026-10-05

1. 摘要

本轮测试主要比较没有投机探索的 Baseline 与当前 Speculate 实现，而不是只验证功能能否运行。

排除短事实题的随机猜值样本和无 token 的确定性故障注入后，两组各包含 13 次正式提交：

指标 Baseline Speculate 变化
Enter 到完整回答累计 143.355 s 107.892 s -24.7%
可观测 tokens 23,863 26,388 +10.6%
可观测成本 $0.00858 $0.00954 +11.2%

当前 Speculate 可以概括为：用约 11% 的可观测成本增长，换取约 25% 的 Enter 后等待时间下降。它不适合全局开启，最有价值的场景是连续调试、意图反转、外部修改后的追问和跨主题追问。

2. 测试设计

2.1 对照组

  • Baseline：不启动 Explorer，artifact_limit=0，近似没有投机探索和 Artifact 注入的原始执行路径。
  • Speculate：使用同一请求和内容相同的独立工作区，在提交前给予 Explorer 固定探索窗口。
  • 标准探索窗口为 6 秒；模拟快速提交的短请求使用 1 秒窗口。
  • 主性能指标是 Enter 到完整回答的延迟，提交前探索窗口不计入该指标。

2.2 运行配置

  • 模型：gpt-5.6-luna
  • Reasoning effort：low
  • 单次最大输出：1,200 tokens
  • Python：项目 .venv，基于 Conda Python311
  • 写权限：只有连续调试场景允许在隔离工作区写入，其余真实场景均为 deny
  • 工作区：每个变体使用独立生成的微型 monorepo，避免缓存和修改互相污染

合成仓库包含：认证缺陷与测试、本地缓存、共享配置、API 和 Worker 消费者、40 个无关服务目录，以及一个 900 行大文件。

2.3 成本口径

按以下标准单价估算：

  • Input：$0.20 / 1M tokens
  • Cached input：$0.02 / 1M tokens
  • Output：$1.20 / 1M tokens

只统计 provider 返回 usage 的请求。Speculate 组有 15 次被取消的 Explorer 没有最终 usage，因此本文中的 Speculate 成本是可观测下界。

3. A/B 结果

下表百分比均为 Speculate 相对 Baseline，负数表示减少。只有两组答案都满足质量检查时，性能差异才作为有效结果。

场景 Baseline Enter Speculate Enter 延迟 Tokens 成本 质量结果
连续调试，两轮合计 25.056 s 18.673 s -25.5% +11.1% +11.9% 均正确定位、修改并通过测试
同文件、不同意图，两轮 18.719 s 17.624 s -5.8% -11.1% +1.3% 安全与性能回答均正确
运行中意图反转 21.812 s 16.247 s -25.5% -6.3% -13.6% 均遵循最终本地缓存意图
Monorepo 跨包链路 16.772 s 14.460 s -13.8% +33.5% +25.1% 均找到两个消费者
大文件窄查询 5.315 s 3.486 s -34.4% +11.9% +42.0% 均命中第 778 行
外部修改后再分析，两轮 10.071 s 3.940 s -60.9% +8.0% +6.4% 均读取到修改后的实现
跨主题追问，两轮 15.655 s 5.702 s -63.6% +96.6% +85.7% 均正确；Speculate Artifact 增至 2 份

全量 15 次正式提交口径下，Enter 延迟降低 24.3%，token 增加 10.4%，可观测成本增加 11.1%。Baseline 完成 37 次模型调用；Speculate 完成 23 次 Committed 调用和 12 次 Explorer 调用，另取消 15 次 Explorer。投机探索减少了正式阶段调用，但增加了总 provider 请求数。

4. 场景分析

4.1 连续调试

两组均先定位 validate_token 使用 startswith 导致的前缀误判，再修改为精确比较并运行针对性测试。Speculate 将两轮 Enter 延迟降低 25.5%，代价是 token 和成本各增加约 11%。这是较符合预期的延迟换成本场景。

4.2 意图变化

同文件从安全分析切换到性能分析时，Speculate 仅快 5.8%，不足以排除单轮网络波动。运行中的目标从 Redis 方案反转为本地缓存分析时，旧 Explorer 被取消，新 Explorer 启动，最终延迟、token 和成本同时下降；这是本轮唯一三项指标均明显改善的真实场景。

4.3 大仓库与大输出

Monorepo 跨包分析的 Enter 延迟下降 13.8%，但成本增加 25.1%。大文件使用窄查询时延迟下降 34.4%，成本增加 42%。另一次功能边界测试强制先宽读 400 行，16K 工具上下文预算在约第 81 行截断，模型无法回答第 778 行的问题；改用 grep 窄查询后可以正确回答。

这说明硬预算能限制最坏成本，但预算耗尽后完全关闭工具会牺牲恢复能力。生产实现应预留一次只允许 grep 或窄范围 read_file 的恢复轮次。

4.4 缓存复用与修改

外部修改后的第二轮分析中，Speculate 延迟降低 60.9%，且没有复用旧实现。确定性测试也确认文件哈希变化后旧 Evidence 的可复用条目降为 0，并产生 stale unresolved。

跨主题追问获得最大延迟收益，但 token 和成本接近翻倍。第二轮缓存命中后 Artifact 从 1 份增长到 2 份，新 Artifact 还混入了仅来自宽泛文件清单的无关 large_module.py 路径。当前缓存仍缺少 evidence 级去重和 glob Evidence 质量过滤。

4.5 输出长度

一句话答案的 Enter 延迟下降 48.1%，但成本增加 31.3%。详细回答只快 1%，说明最终长文本生成几乎完全掩盖投机探索收益。已要求详细输出的请求不适合默认投机，控制最终 output tokens 比提前探索更有效。

5. 短请求异常

DEFAULT_TTL 数值问题连续运行 5 组。Explorer 在 1 秒窗口内均未产生 Artifact，Committed 也没有调用读取工具，而是直接生成数值：

指标 Baseline Speculate
正确次数 4/5 2/5
Enter 延迟中位数 3.406 s 1.993 s

Speculate 中位延迟低约 41.5%，但正确率不可接受，不能视为有效性能收益。错误不是由 Artifact 污染造成的，两组都存在未读取文件而直接猜值的问题。对可精确读取的事实题，应要求 Committed 至少执行一次窄 grep 或 read_file，并跳过 Explorer。

6. 功能边界

除性能 A/B 外，还验证了以下控制和降级行为：

  • 连续修改后针对性测试通过，受影响 Artifact 同步失效并可后台刷新。
  • 运行中意图反转会取消旧 Explorer，并为新目标建立探索任务。
  • 外部文件修改会通过内容哈希使旧 Evidence 失效。
  • Judge、Summary 和 Explorer 连续故障时，Committed Agent 仍能完成降级提交。
  • 16K Committed 工具上下文预算会截断宽读结果，并提示模型缩小查询。
  • 短请求提交时仍在运行的 Judge 或 Explorer 能被取消，不阻塞正式提交。

7. 结论与策略

Speculation 不应作为全局默认开关，而应由请求特征和已有状态选择性启用：

请求类型 建议
连续调试、近期追问、修改后再分析 开启
意图已较稳定且需要多文件读取 开启，但限制 Explorer 调用数
跨主题共享证据 有条件开启，先修复 Evidence 去重
短事实题 关闭，直接执行窄读取
明确要求详细长报告 关闭或降低探索预算
成本优先的 Monorepo / 大文件分析 默认关闭，按延迟目标手动开启

后续优化优先级：

  1. 为精确事实题增加强制验证策略，禁止无证据直接生成数值。
  2. 按 (path, content_hash, claim) 合并 Evidence，过滤只有文件名的 glob 证据。
  3. 用已完成 Explorer 调用数或已获得 Evidence 数量控制投机预算，而不是只依赖固定时间窗口。
  4. 工具预算耗尽前保留一次窄查询恢复机会。
  5. 连续运行 10-20 轮并报告 P50/P95，同时从 provider 账单校准取消请求的真实成本。
